# Android-панель MAX Postiz 0.1.6

Панель M1 подключается к серверному шлюзу, показывает календарь, резерв,
адресатов и очередь MAX, Telegram, VK и Пикабу. Команды появляются в карточке
только при наличии полномочий и поддержки конкретного состояния. Шлюз
использует тот же PostgreSQL и доменные проверки, что и редакция Postiz.

- [Техническое задание](TECHNICAL_SPEC.md)
- [Контракт интеграции и сценарии приёмки](INTEGRATION.md)
- [OpenAPI, сгенерированный из кода шлюза](openapi.json)

## Шлюз в Docker

Мобильный сервер поставляется отдельным контейнером. Он обслуживает API,
использует ту же PostgreSQL и те же доменные проверки, что и редакция.
Обработчики отправки и подготовки остаются в редакции. Существующую базу
подключают после проверенной резервной копии и миграции по процедуре проекта.
При запуске шлюз проверяет наличие схемы `0010` и состояние редакции.

Для запуска нужен Docker Compose 2.33.1 или новее.
[Требования Docker Compose](https://docs.docker.com/reference/compose-file/services/#gw_priority)

Собрать [образ](../deployment/mobile/Dockerfile) и запустить сервис из
[Compose](../deployment/mobile/compose.yaml) на Linux amd64. Для сборки нужна база
Python 3.12. Принятый образ и базовый образ фиксируют по digest. Контейнер
использует `requirements.lock` и `requirements-browser.lock`. Браузерный
слой устанавливает Chrome и Chromium, точную версию Chrome фиксируют при
приёмке образа.

| Переменная Compose | Назначение |
| --- | --- |
| `MOBILE_RUNTIME_ROOT` | Абсолютный путь к подготовленной редакции той же версии с `TOPIC.md`, `config/`, `schemas/`, `prompts/`, `alembic.ini`, `migrations/` и `data/` |
| `MOBILE_RUNTIME_UID`, `MOBILE_RUNTIME_GID` | Непривилегированные UID и GID владельца runtime. Им доступны общие блокировки профиля и журналы |
| `MOBILE_PROJECT_NETWORK` | Существующая приватная Docker-сеть редакции, в которой доступны PostgreSQL и Postiz |
| `MOBILE_RUNTIME_ENV_FILE` | Абсолютный путь к приватному файлу окружения шлюза, с `DATABASE_URL` и служебным доступом к Postiz |
| `MOBILE_BROWSER_SECCOMP_PROFILE` | Абсолютный путь к проверенному профилю seccomp с необходимыми вызовами для песочницы Chrome |
| `MOBILE_PYTHON_BASE` | Образ Python 3.12. При приёмке указать точный digest |

`DATABASE_URL` и `POSTIZ_BASE_URL` внутри контейнера должны использовать
сервисные имена в приватной Docker-сети. У шлюза есть отдельная bridge-сеть
для порта `127.0.0.1:8093` и исходящего доступа к провайдеру входа и площадкам.
Эта сеть позволяет опубликовать loopback-порт, даже если сеть редакции
помечена `internal`. Например, если в сети редакции доступны
`hub-postgres` и `postiz`, адрес API Postiz — `http://postiz:5000/api/public/v1`.
Адрес редакции для пользователя при этом сохраняется. Compose монтирует
`MOBILE_RUNTIME_ROOT` в контейнер по тому же абсолютному пути. Браузерные
журналы используют этот путь при проверке сохранённых доказательств. Шлюз
использует общий каталог `data/` с журналами, медиа и владельческими
браузерными профилями.
Перед включением команд проверить совместимость версии и формата профиля,
доступ к владельческому ключевому хранилищу, общий файловый lock и запуск
Chrome под UID сервиса с включённой песочницей. Отсутствие проверяемого
профиля ограничивает браузерную сверку.

Контейнер сбрасывает все Linux capabilities. В профиле seccomp системный
вызов `chroot` должен быть разрешён для песочницы Chromium без условия
`CAP_SYS_CHROOT` на контейнере. Ядро проверяет права на этот вызов внутри
пользовательского пространства имён. Для Playwright 1.63.0 использована
следующая правка официального профиля с сохранением остальных правил.
[Профиль Playwright 1.63.0](https://github.com/microsoft/playwright/blob/v1.63.0/utils/docker/seccomp_profile.json)

```bash
python3 - "$PLAYWRIGHT_SECCOMP_PROFILE" "$MOBILE_BROWSER_SECCOMP_PROFILE" <<'PY'
import json
import sys
from pathlib import Path

profile = json.loads(Path(sys.argv[1]).read_text(encoding="utf-8"))
assert profile["defaultAction"] == "SCMP_ACT_ERRNO"
[rule] = [rule for rule in profile["syscalls"] if rule["names"] == ["chroot"]]
assert rule["action"] == "SCMP_ACT_ALLOW" and rule["includes"] == {"caps": ["CAP_SYS_CHROOT"]}
rule["includes"] = {}
with Path(sys.argv[2]).open("x", encoding="utf-8") as output:
    json.dump(profile, output)
PY
```

В приватном окружении шлюза задать также параметры мобильного входа.

| Переменная | Назначение |
| --- | --- |
| `MOBILE_ENVIRONMENT_ID` | Уникальное имя окружения для журнала и Android |
| `MOBILE_OIDC_ISSUER` | Точный HTTPS issuer провайдера входа |
| `MOBILE_OIDC_INTROSPECTION_URL` | HTTPS endpoint на том же origin, что и issuer |
| `MOBILE_OIDC_INTROSPECTION_CLIENT_ID`, `MOBILE_OIDC_INTROSPECTION_SECRET` | Закрытые учётные данные серверной проверки токена |
| `MOBILE_OIDC_ANDROID_CLIENT_ID` | Публичный native client ID для Code + PKCE S256 |
| `MOBILE_OIDC_AUDIENCE` | Уникальная audience access token для шлюза конкретного окружения |
| `MOBILE_OIDC_SUBJECT_ROLES` | JSON-словарь OIDC subject → роль для одного окружения. Ровно один `owner` |
| `MOBILE_WRITE_ENABLED` | Только значение `true` включает команды. Стандартный режим — чтение |

Провайдер входа должен возвращать из интроспекции `active`, `iss`, `aud`,
`client_id`, `sub`, `exp`. Для возобновления и вывода DRAFT из обработки
владелец проходит свежий вход. Шлюз проверяет `auth_time` в пределах пяти
минут. `operator` получает паузу, ручную блокировку и сверку. `viewer`
и `editor` используют чтение в M1. В журнале показывается связанный с
провайдером псевдоним оператора, владелец видит историю окружения.

```bash
docker compose -p max-postiz-mobile -f deployment/mobile/compose.yaml up --build --wait -d
```

На хосте порт опубликован на `127.0.0.1:8093`. На частном HTTPS origin
через VPN проксировать только `/mobile/v1/` на этот порт. В прокси
исключить из журналов заголовок Authorization и тела запросов. Контейнер
мобильного шлюза публикует один порт. Внутренние API редакции и Postiz Bridge
доступны в своих сегментах.

## Сборка и подключение Android

Нужны JDK 17, Android SDK 37, Gradle Wrapper из репозитория. На Windows
при ошибке AGP из-за нелатинских символов использовать рабочий путь с
латиницей. В директории `android_panel` выполнить:

```powershell
.\gradlew.bat :app:assembleDebug
```

Для рабочего входа передать сборке `-PmobileRedirectHost=<домен>`.
На этом домене разместить Digital Asset Links для имени пакета и
отпечатка сертификата конкретной сборки. В OIDC зарегистрировать точный
callback `https://<домен>/android/oidc-return`. В приложении заполнить
HTTPS-адрес шлюза, issuer и публичный client ID. Ключ подписи хранится
отдельно от исходников. Приватные адреса и учётные данные задаются на
стороне окружения.

## Частная сборка без домена

Для сети редакции предусмотрена отдельная release-сборка. Она использует
HTTPS на `10.20.30.45` и выделенный realm `max-postiz-mobile`. Провайдер
открывается в системном браузере. Возврат идёт по точному URI
`ru.maxpostiz.panel:/oauth2redirect`. Проверяются PKCE S256 и состояние
запроса. Профиль использует обычную OIDC-сессию и scope `openid`.
[OAuth для нативных приложений](https://www.rfc-editor.org/rfc/rfc8252.html)

```powershell
.\gradlew.bat :app:assembleRelease -PmobilePrivateLan=true -PmobilePrivateCa=<путь-к-публичному-CA-PEM>
```

В APK помещается только публичный сертификат CA. Он применяется к
`10.20.30.45`. Подписывать APK ключом этой установки. Для браузера Android
установить выданный публичный `.cer` как сертификат CA в том же профиле,
где открывается вход. Пользователь входит из локальной сети или через
разрешённый VPN-адрес. Рабочая панель Postiz сохраняет прежний адрес.
[Доверенные сертификаты Android](https://developer.android.com/privacy-and-security/security-config)

Статус окружения шлюза виден в приложении. Идентификатор
`vm112-db-copy-readonly` означает снимок очереди с отключёнными командами.
Подключение к рабочей БД требует отдельной проверки версии редакции,
схемы, активных claims и неизвестных исходов.

## Изолированная проверка в Docker

[Compose-стенд](../deployment/mobile/compose.fixture.yaml) использует тот же
установленный пакет, API, доменные операции и миграции. Синтетические площадки
и проверка токена заменяются адаптерами стенда. PostgreSQL находится только
во внутренней сети и не публикует порт. У шлюза есть дополнительная сеть
для порта `127.0.0.1:18094` с отключённым исходящим IP masquerading.
Выполнить из корня checkout в Linux или WSL.

```bash
install -d -m 700 .test-state/mobile-docker
export MOBILE_FIXTURE_PG_PASSWORD_FILE="$PWD/.test-state/mobile-docker/postgres-password"
if [ ! -e "$MOBILE_FIXTURE_PG_PASSWORD_FILE" ]; then
  python3 -c 'import secrets; print(secrets.token_urlsafe(32))' > "$MOBILE_FIXTURE_PG_PASSWORD_FILE"
fi
chmod 644 "$MOBILE_FIXTURE_PG_PASSWORD_FILE"
docker compose -p max-postiz-mobile-fixture -f deployment/mobile/compose.fixture.yaml up --build --wait
docker compose -p max-postiz-mobile-fixture -f deployment/mobile/compose.fixture.yaml exec -T \
  mobile-fixture cat /fixture/runtime/fixture-access.private.json > .test-state/mobile-docker/fixture-access.private.json
adb reverse tcp:18094 tcp:18094
```

Секрет читают оба непривилегированных процесса контейнеров. На хосте
доступ к файлу закрывает каталог с режимом `0700`. Для следующего чистого
прогона удалить только том тестового проекта командой `docker compose -p
max-postiz-mobile-fixture -f deployment/mobile/compose.fixture.yaml down -v`.

В отладочном APK выбрать вход со стендом, адрес `http://127.0.0.1:18094`
и токен из `fixture-access.private.json`. Этот режим доступен только в
отладочной сборке. Проверить четыре адресата, календарь, ручную блокировку
черновика Пикабу, её снятие, сверку Telegram и сохранение неизвестного
исхода при недостаточном доказательстве. Все ответы платформ на стенде
синтетические.

## Нестабильное соединение

При временном сбое Android повторяет чтение один раз с короткой паузой. Он
учитывает `Retry-After` и при долгом ожидании показывает ошибку. Последний
снимок с временем чтения остаётся на экране. Кнопки изменения снова
доступны после успешного обновления.

До отправки подтверждённой команды Android сохраняет её ID и параметры
в зашифрованном хранилище. После обрыва или перезапуска читает статус по
тому же ID. Если сервер не нашёл запись и срок плана не истёк, оператор может
вручную отправить ту же команду. Шлюз привязывает её к прежнему
`operation_id`. Операции с неизвестным исходом требуют сверки.

Для просроченного или старого плана Android сверяет статус с учётом ID и хеша плана.
Ожидание завершается, когда шлюз подтверждает истечение срока и то, что команду не принял.
Если шлюз не может это подтвердить, ожидание сохраняется.

## Границы M1

При первом открытии Android-панель предлагает задать четырёхзначный PIN.
Он запрашивается до экрана подключения и при возврате после сворачивания.
Для сброса PIN нужно подтвердить системную блокировку телефона.

Поставьте галочку «Запомнить имя и пароль», введите оба поля на экране
подключения и нажмите «Войти». Данные сохраняются на телефоне и шифруются
ключом Android Keystore. Сохранённый пароль отмечен под полем ввода.
После перезапуска достаточно разблокировать панель PIN. Приложение само
восстанавливает сохранённую серверную сессию. При временном обрыве сети
данные сессии сохраняются для повторного подключения.
После отзыва или истечения сессии нужен новый вход в Keycloak.
Если после нажатия «Войти» открывается Keycloak, приложение передаёт браузеру
имя и копирует пароль без предпросмотра. Вставьте пароль в форму и подтвердите
вход. При возврате приложение очищает свою запись буфера. Чтобы удалить
сохранённые данные, снимите галочку и нажмите «Войти».

Для частной сборки `-PmobilePersistentLanSession=true` включает запрос
`offline_access` при сохранении входа. Перед такой сборкой необходимо выдать
этот optional scope и роль `offline_access` выделенному мобильному клиенту
Keycloak. Роль также должна быть у владельца. Для HTTPS-маршрута
`/realms/max-postiz-mobile/protocol/openid-connect/revoke` разрешите POST
с теми же ограничениями частного доступа, что и для входа. Ротация refresh
token и требование свежего входа для защищённых команд сохраняются.
«Выход» удаляет локальную сессию и запрашивает её отзыв. Вход после обновления
старой сессии потребуется один раз для получения длительной сессии.

Действия над проектом видны в «Обзоре». Блокировка и сверка находятся в
верхней части карточки записи. Доступность кнопок определяется правами,
состоянием записи и ответом шлюза. В режиме чтения видны причины ограничений.

Блокировка записи доступна для связанных MAX-записей с проверяемым барьером
и допустимых локальных записей Telegram, VK и Пикабу. Снятие блокировки
для очереди проверяет подписанную дату. Если время прошло, запись остаётся
удержанной. Для неё нужна отдельная операция отмены и перепланирования,
которая выходит за пределы M1. Сверка на площадке может подтвердить
доставку только по точному доказательству. В MAX журнал старого формата
без доказательств оставляет статус неизвестным. Вывод MAX DRAFT без
отправки доступен по отдельному доказательному плану до согласования.

Рабочая эксплуатация требует частного HTTPS, проверенной связки OIDC,
установленного Postiz и проверки маршрутов конкретного окружения.
Для браузерной сверки VK и Пикабу Linux-процессу нужны отдельная cgroup v2
с правом создать дочернюю группу и возможность безопасно завершить её через
`cgroup.kill`. Стандартный Compose запускает шлюз с закрытой cgroup. В такой
среде карточка сообщает причину и закрывает только команду браузерной сверки.
Календарь, очередь, пауза и ручная блокировка этих площадок доступны по их
обычным проверкам. MAX, Telegram и VK API используют собственные механизмы
сверки. Квитанция без подтверждённого чтения сохраняет неизвестный исход.
Для включения браузерной сверки нужны проверка делегирования и отдельная
приёмка среды исполнения.

Редактирование и согласование публикаций относятся к M2.
