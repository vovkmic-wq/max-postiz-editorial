# Почасовая серия перевода и публикации MAX–Postiz

По прямому поручению владельца от 17 октября 2026 выбирай одну новую для
канала англоязычную статью, передавай её проекту для перевода, проверяй текст
и публикуй в MAX через календарь Postiz не чаще одного раза за 3600 секунд.
Контролируй выполнение и исправляй выявленные ошибки. Применяй AGENTS.md.
Пробуждение настроено на пятую минуту часа; готовь материал заранее, сохраняя
интервал по фактической последней публикации, а не по времени старта подготовки.

Проект: C:\script\20261011-Max postiz. Рабочая Linux VM:
editorial@10.20.30.45, каталог /opt/max-postiz. Используй SSH key
data/linux-vm_ed25519 с UserKnownHostsFile=data/linux-vm-known-hosts,
StrictHostKeyChecking=yes. Не выводи пароли, ключи, cookies и .env.local.
Hub http://10.20.30.45:8090/hub; Postiz http://10.20.30.45:4007/launches.
Адресат только max_test, канал https://max.ru/channel_neurovideo_max.

Если VM по SSH недоступна, выполни локальный scripts/check-network.py,
сохрани отчёт только в ignored data и сверяй docs/NETWORK_RECOVERY.md.
Различай недоступность Proxmox и его гостей от состояния отдельного GPU
и VPN: конкурирующие маршруты сами по себе не доказывают отказ туннеля.
При недоступной VM не запускай новую подготовку или публикацию; после
возврата связи сначала сверяй прерванную запись. При неизменном уже
сообщённом сетевом ожидании оставайся без уведомления.

Перед новым материалом проверь status предыдущей записи через
scripts/hourly_article_test.py и выполненные dispatches в БД. Если предыдущая
отправка sending/unknown, mutation lease активна или результат не сверён,
не создавай следующую публикацию. Не считай pending, owner_attested, доступ
к каналу или отсутствие исключения доказательством доставки. После published
нужны verified dispatch, Postiz PUBLISHED и фактический текст в канале;
затем верни только max_test на паузу. Сохраняй доказательства в ignored data.

Выбирай англоязычный научный материал NASA SVS, например через его обычный
поиск. Открой страницу и проверь, что narrative-текст относится к NASA SVS,
нет отдельного copyright/стороннего ограничения; проверь актуальные условия
https://svs.gsfc.nasa.gov/help/. Не скачивай изображения, видео и музыку.
Темы: наука, интересные истории, юмор; исключай политику, NSFW и опасные
практические советы. Ранее опубликованная дата допустима для научного
объяснения, но не называй такой материал свежей новостью. Новизна означает
отсутствие публикации в этом канале и в журнале цикла.

Передай одну выбранную ссылку scripts/fetch_nasa_article.py, сохрани input
JSON только в data, затем запусти prepare через scripts/hourly_article_test.py
по его --help. Проект сам вызывает Qwen, отдельный Ministral и LanguageTool.
Helper принимает полные narrative widgets Basic text и Basic text with HTML;
media captions и поисковые excerpts не являются заменой статьи. При редактуре
сохраняй точную запись чисел исходника, включая десятичную точку. Нормализация
однозначных issue-объектов рецензии сохраняет её решение и все замечания;
отрицательный ответ не становится согласованием. Не добивайся другого решения
повторной рецензией неизменённого отклонённого текста.
Проверь готовый вариант по исходнику: смысл, числа, связность, русский язык,
ссылка и честная маркировка перевода. Не подменяй отказ проверки фиктивным
согласием и не выдавай чужой перевод за собственный оригинал.

Только после проверки точного текста используй publish с reviewed-hash,
возвращённым prepare/status. Это сохраняет конкретное согласование версии,
времени и max_test по делегированному поручению. Один вариант должен создать
ровно одну запись Postiz QUEUE, после чего отправляет существующий worker.
Не запускай дополнительный worker или широкий tick ради этого теста.
Ожидай результат короткими проверками и сверяй Postiz и MAX. При unknown
запрещено повторять отправку; используй штатную сверку и фактический канал.

Для следующего часа выбирай другой URL и другой материал. Журнал цикла
отсекает URL, исходный текст и перевод, а также повторный запуск того же часа.
Пропущенные часы не догоняй. Если допустимого нового материала нет, пропусти
запуск. После подтверждённой предыдущей доставки новый материал текущего
часа можно подготовить заранее. Publish назначает отправку не раньше
max(текущее время + 120 секунд, последняя фактическая публикация + 3601 секунда).
Ранний запуск подготовки не разрешает раннюю отправку. Истёкший слот не
переноси; при незавершённой или неопределённой доставке новую цепочку не запускай.
Начать publish нужно в текущем зарезервированном часу, но назначенная штатным
кодом отправка может прийтись на следующий час. Уже созданную и согласованную
отправку не отменяй и не пересоздавай только из-за смены часа; контролируй её
фактический результат. Это не разрешает переносить истёкшую локальную подготовку.

При ошибке сначала собери минимальные приватные логи и найди причину.
Безопасные исправления кода/конфигурации делай самостоятельно, обновляя
CHANGELOG.md, согласованную версию, проверки и GitHub. Перед заменой runtime
проверь sending/unknown и leases, сделай закрытый backup, перезапускай только
необходимые службы. Не меняй текст уже отправленного поста без сверки.
Сообщай об успешной проверенной публикации, исправленной существенной ошибке
или необходимом действии владельца; при неизменном ожидании не уведомляй.
Reddit API и прежнюю четырёхчасовую автоматизацию этим сценарием не включай.

Если подготовка прервалась ДО создания Draft/Variant и любых внешних операций,
сверь это по журналу и БД. Для той же записи в текущем часу можно явно
выполнить prepare того же input JSON с --retry-record RECORD_ID. История
ошибки сохраняется, новый слот не создаётся. После создания варианта, при
другом исходнике/политике или истёкшем часу эта команда откажет; не обходи отказ.
Если status вернул prepared для текущего часа, продолжай проверку этого текста,
а не создавай второй prepare. При ошибке генерации учитывай профиль моделей
scripts/configure_article_models.py и лимит ожидания 600 секунд; согласование
и контроль фактической отправки остаются обязательными.

Если нужна редакторская правка уже prepared текста, сохрани точные title/body
по-русски (без добавленного приложением footer) в ignored data/correction.local.json
и используй revise-prepared RECORD_ID data/correction.local.json. Этот путь
заново проверяет исправленный текст независимой моделью и LanguageTool,
фиксирует новую версию и hash. Не меняй prepared_hash напрямую. Только после
успешной проверки используй новый hash и проверяй новый точный текст.

Истёкшую или отклонённую запись prepared можно закрыть abandon-prepared
RECORD_ID --reason TEXT только после доказанного отсутствия Postiz/dispatch/
approval и mutation lease. Если осталась только неудачная подготовка без
варианта, используй cancel-preparation. Обе команды сохраняют журнал,
исходник и использованный час; затем в следующем свободном часу выбирай
другой материал. Не переноси старую публикацию в новый слот обходом журнала.

Если prepare отклонил уже созданный моделью перевод до Draft/Variant, можно
отредактировать его по реальному исходнику и замечаниям и выполнить prepare
того же input с --retry-record RECORD_ID --candidate data/correction.local.json.
Кандидат проверят независимая модель и LanguageTool без нового перевода;
это явная аудируемая редактура с честной provenance. Сохраняй числовую запись
исходника (например, 11:59 p.m. → 11:59 вечера), поскольку действующий gate
сравнивает точные numeric tokens. Не отключай проверки ради принятия текста.
После ARTICLE_QUALITY_REJECTED обычный retry без --candidate не разрешён.
Предоставляй изменённую по реальным замечаниям редакцию: сохранённый хеш
отклонённого кандидата блокирует повторную рецензию того же текста.

После повторных замечаний, противоречащих точному исходнику и переводу,
не подбирай формулировки ради случайного согласования. Сохрани все отказы,
сверь отсутствие локального варианта и внешних операций, затем штатно закрой
pre-draft запись. Этот источник и час остаются использованными. Изменения
процедуры проверяй на отдельных новых контрольных текстах; не пересэмплируй
отменённую статью и не удаляй её замечания. При тайм-ауте генерации отдельно
проверь OpenCode sessions и idle backend/router queue: общий router может
дочитывать активный inference после отключения клиента. До idle новой
генерации нет; HTTP health не доказывает завершение старой генерации.
