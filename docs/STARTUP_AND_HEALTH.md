# Автозапуск редакции и проверка после загрузки сервера

С 18 октября 2026 действует пауза всех заданий проекта по указанию владельца.
Автозапуск панелей и БД сохранён, но Hub запускается с `--no-worker` через
`/etc/systemd/system/max-postiz-hub.service.d/90-owner-pause.conf`. Эталон:
[max-postiz-owner-pause.conf](../deployment/linux/max-postiz-owner-pause.conf).
Почасовая политика выключена и все адресаты на паузе; heartbeat `max-postiz`
имеет статус `PAUSED`. Пауза worker сохраняется после перезагрузки VM.

Для полной паузы Postiz Linux compose также задаёт `RUN_CRON: ''` и
`EXCLUDE_QUEUE` со всеми 36 очередями установленного custom image, включая
`main`, `max` и почтовые очереди. Это отключает workers, сохраняя frontend,
backend и Temporal history. Открытые workflow не удаляются: три служебных
workflow могут оставаться в состоянии running, ожидая выключенных workers.
Строка `RUN_CRON='false'` не подходит: в этой версии проверяется truthiness.
При обновлении custom image список очередей нужно сверить заново; текущий
профиль не является универсальным выключателем произвольных будущих версий.

Проверка на VM: `systemctl show max-postiz-hub.service -p ExecStart` должен
показать `--no-worker`; `is-active` и HTTP 200 подтверждают доступность панели,
но не выполнение задач. Очереди и историю не удаляют. При новом прямом
поручении владельца возобновить работу сначала сверяют sending/unknown,
mutation leases, Postiz и фактический MAX. Затем отдельно восстанавливают
нужные политики/адресатов, снимают этот drop-in и перезапускают существующий
Hub. Для Postiz отдельно разрешают только очереди нового согласованного
маршрута, оставляя остальные в EXCLUDE_QUEUE, и пересоздают только его
контейнер. RUN_CRON включают лишь при отдельном разрешении фоновых задач.
После этого включают только
согласованную автоматизацию. Не возобновлять
автоматически по старому heartbeat и не догонять пропущенные часы.

Актуально на 15 октября 2026 для Proxmox `10.20.30.142`, VM 109 с Qwen и
model-router, VM 112 с Postiz и редакцией, а также отдельного физического
GPU-узла `10.20.30.143` с Ministral. При загрузке Proxmox `pve-guests.service`
запускает VM 109 первой (`order=10`, ожидание 90 секунд), затем VM 112
(`order=20`, ожидание 30 секунд). VM 110 остаётся выключенным резервом.
Контейнер 111 ComfyUI уже имеет собственный автозапуск `order=60`; для
обычных текстовых публикаций он не требуется.

Настройка Proxmox закреплена в
[`deployment/linux/configure-proxmox-autostart.sh`](../deployment/linux/configure-proxmox-autostart.sh).
Скрипт сверяет имена VM и включённую службу `pve-guests`, сохраняет прежние
конфигурации в `/root/` с правами 0600, выставляет `onboot` и порядок запуска.
Он не перезагружает и не запускает гостевые системы. Для восстановления
установки его запускают от root на том же Proxmox host. Новая VM 112 также
получит нужный порядок при создании через `provision-proxmox.sh`.

В VM 109 службы `model-router.service` и `llama-server@qwen35-9b.service`
включены в systemd. Основная модель доступна через
`http://10.20.30.95:8083/v1`; в этом API также есть совместимое имя
`qwen25-coder-7b` для Ministral. Сама Ministral работает на отдельном
физическом узле `10.20.30.143`, не в Proxmox VM. Его служба по действующей
конфигурации узла запускается при загрузке этого компьютера. Proxmox не может
включить отдельный выключенный компьютер и не задаёт настройки его BIOS.

В VM 112 включены Docker, nginx, Hub, OpenCode и LanguageTool. Восемь основных
контейнеров Postiz, PostgreSQL, Redis и Temporal используют `restart: always`
и healthchecks. Службы Xvfb, VNC и noVNC теперь также включены при загрузке;
они слушают только локальные сокеты и доступны владельцу через защищённый
Hub proxy. Вход владельца в MAX по QR/телефону остаётся отдельным действием:
`max-postiz-login.service` не запускается автоматически. После перезагрузки
может потребоваться повторный вход в MAX; статус сервисов не подтверждает
действительность браузерной сессии.

## Проверка с рабочего компьютера Windows

Если SSH к VM вообще не открывается, сначала выполните локальную
[сетевую диагностику](NETWORK_RECOVERY.md). Она работает при выключенной VM
и сравнивает доступность Proxmox, гостевых систем и отдельного GPU-узла;
недоступность общего API не означает автоматически отказ клиентского VPN.

Из корня проекта выполните:

```powershell
.\scripts\check-startup.ps1
.\scripts\check-startup.ps1 -Deep
```

Скрипт использует игнорируемый локальный SSH-ключ `data/linux-vm_ed25519` и
закреплённый host key из `data/linux-vm-known-hosts`, запускает
`deployment/linux/check-stack.py` внутри VM 112 и печатает JSON. Он ничего
не публикует и не меняет состояние. Код завершения `0` означает успешные
проверки; `1` — как минимум один сбой. Запуск напрямую внутри VM:

```sh
python3 /opt/max-postiz/deployment/linux/check-stack.py
python3 /opt/max-postiz/deployment/linux/check-stack.py --deep
```

Обычный режим проверяет `enabled` и `active` восьми systemd-сервисов,
`running` и `healthy` восьми основных Docker-контейнеров, HTTP 200 для Hub,
Postiz, OpenCode, LanguageTool, model-router и backend Ministral, наличие
обоих нужных ID в `/v1/models`, TCP-доступность Proxmox и SSH VM 112.
`-Deep` дополнительно получает короткий реальный ответ каждой модели через
общий API. Для Qwen проверка отключает режим скрытого рассуждения в данном
запросе, чтобы короткий лимит токенов не давал ложный пустой ответ. Прокси
рабочего компьютера не используется для локальных адресов.

Проверка `-Deep` подтверждает текущую доступность двух моделей и панелей.
После изменения настроек VM 112 была отдельно перезагружена: systemd-службы
и Docker-контейнеры поднялись сами, Temporal прошёл состояние `starting`,
а повторный `-Deep` завершился с кодом 0 и ответами обеих моделей. Это
проверка перезапуска гостевой системы, не выключения физического Proxmox.
Она не доказывает, что после аварийного отключения питания гарантированно
сохранилась сессия MAX, что уже запланированный пост доставлен, или что
отдельный физический GPU-узел сам включится после подачи питания. После
реального перезапуска проверяйте доступ к MAX отдельно, а отправку — по
фактическому сообщению в канале и статусам Hub/Postiz. Не снимайте паузу
канала и не повторяйте `unknown` только на основании зелёного healthcheck.

Перед изменением автозапуска исходное дерево сохранено в GitHub tag
`v0.6.0-pre-autostart-20261015`; конфигурации VM сохранены локально на Proxmox
в `/root/109.conf.before-editorial-autostart-*` и
`/root/112.conf.before-editorial-autostart-*`. Секреты, cookies и runtime
отчёты не входят в исходный архив.
