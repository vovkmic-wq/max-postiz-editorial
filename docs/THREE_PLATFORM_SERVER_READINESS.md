# Перенос существующих MAX, Telegram и VK — 0.14.0

## Статус приёмки

Приёмка определяется приложенным `acceptance.json` для точного исходного дерева и
артефакта. Без `accepted=true`, `native_checks_passed=true`, успешных cleanup/privacy
проверок и совпадающих image ID / SHA архива установка имеет статус **NOT_ACCEPTED**:
команды переключения не выполняются. Подлинность и успешное завершение GitHub run
владелец проверяет отдельно. Исходный пакет и unit-тесты сами по себе не являются
приёмкой образа. Перенос на рабочий сервер требует отдельного разрешения владельца.

Для окончательного source также обязательны полный CI и отдельный PR check
`CodeQL` без новых блокирующих alerts. Успешные Actions jobs `Analyze` означают
завершение анализа; их статус не заменяет результат code-scanning gate.

Цель — сохранить существующие адресаты, PostgreSQL, Postiz, историю, согласования,
попытки и неизвестные исходы. Это не универсальная установка любых новых аккаунтов.
Пикабу в эту приёмку не входит; его состояние, профиль и историю не изменять.

Сохранённые локальные результаты перед нативной приёмкой приведены ниже. Изменения
startup/runner после этих прогонов требуют нового финального прогона и proof для
точного commit; прежние числа не сертифицируют изменённые байты.

| Проверка | Результат и граница доказательства |
| --- | --- |
| Node: шесть наборов контрактов | 159 passed; mocks, строгий TypeScript, без площадок |
| VK: восемь модулей, включая новый выключенный пример | 587 passed, 1 skipped из-за прав symlink Windows; loopback/временные данные, 17 файлов без изменений во время прогона |
| Owner API / восстановление сохранения | 73 passed; локальные проверки, не перенос рабочей БД |
| Изолированный Docker Engine | 25 passed; pure/mocks, не запуск Linux Docker |
| Сценарий нативной приёмки | 24 passed; pure/mocks, не успешный образ |
| Защиты нативного runner и выдачи artifacts | 19 passed; pure/mocks, не фактическая выдача образа |
| Проверка release identity и handoff | 23 passed; pure/mocks, без Docker и VM |

Новый workflow рассчитан на GitHub-hosted **Ubuntu 26.04 / Docker 29**. Его фактический
результат берётся из принятого proof. Исторические результаты WSL Ubuntu 24.04, проверки supervisor
и прерванные из-за ресурсов R1/R2 не заменяют успешный новый прогон. Логин в реальные
Linux-аккаунты и доставка в существующие каналы после переноса остаются отдельными
проверками владельца. Локальная проверка доступа, API receipt или fixture не равны
независимо подтверждённой публикации.

## Мониторинг из 0.13.3

В исходники 0.14.0 включён отдельный наблюдатель и удалённое управление из
0.13.3. Это host-компонент со своими конфигурацией, SQLite outbox и браузерным
профилем; Docker archive Postiz не устанавливает и не авторизует его автоматически.
Обычные команды наблюдателя только проверяют существующую схему. Создание схемы
разрешено отдельному `init`, миграция — явному обслуживанию копии после backup.

Полная native-приёмка этой редакции дополнительно требует
`checks.monitor_0133_native_copy.passed=true`: новую честно созданную копию,
собственный PostgreSQL на 55448, owner-only API, worker heartbeat, watchdog без
уведомления, restart и восстановление PostgreSQL/SQLite с точной историей.
Основной native-каталог не получает isolation marker задним числом. Существующие
`sending`/`unknown`, pending-команды и сообщения не сбрасываются и не проигрываются
повторно. Рабочий сервер не используется этим сценарием.

В native-сценарии команды и служебные отправки выключены; попытка открыть MAX
или отправить сообщение считается ошибкой проверки. Этот proof подтверждает
интеграцию монитора и восстановление его состояния, но не вход в реальный аккаунт,
получение Android или доставку служебного отчёта. Для живого включения остаются
отдельный профиль, приватный чат и его актуальная привязка по
[ANDROID_MAX_MONITORING](ANDROID_MAX_MONITORING.md). Состояние работающего MAX
не меняется при подготовке, приёмке или восстановлении копии.

## Что сохранить до разрешённого переноса

1. Оставить общий цикл и MAX/Telegram/VK на паузе. Проверить `sending`, `unknown`,
   активных владельцев, mutation/send leases, модельные claims и ближайший Postiz
   `QUEUE`. Активную или неизвестную операцию не сбрасывать и не повторять.
2. Снять согласованные резервные копии **существующих** БД Postiz и редакции,
   uploads, runtime/journals, полных политик и приватных конфигураций. Сохранить
   текущие source commit, фактический старый image ID, compose-файлы и права доступа.
   Проверить чтение backup и процедуру восстановления на отдельном клоне.
3. Не импортировать тестовую SQLite/PostgreSQL, synthetic fixture, cookies Windows
   или `data/` из копии поверх VM. Не переименовывать проект `max-postiz`, базы или
   volumes. Не выполнять `down -v`, prune или очистку очередей/истории.

Секреты и backups остаются локальными приватными файлами. В исходном архиве должны
сохраняться `AGENTS.md`, `CHANGELOG.md` и история версий. Проверка пакета выполняется
для точного commit; требуются совпадающие manifest/хеши source ZIP, sdist и wheel.
Архивы не должны содержать `.env`, profiles, runtime-отчёты, volumes и credentials.

## Принять и выбрать образ

Владелец сначала проверяет успешный GitHub run **для нужного commit и полного
исходного контекста**: полный Next build, запуск настоящих приложений, изолированные
PostgreSQL/Postiz, restore/history/auth/restart, реальное завершение дочерних процессов
и cleanup. Отдельный успешный unit-тест или частичный лог build для этого недостаточен.

Из принятого artifact берутся переносимый Docker archive, его SHA-256 и конечный
`sha256:...` image ID. Если этих значений нет, не заменять их старым tag,
placeholder или промежуточным image. Сохранить полный proof и artifact до истечения
срока хранения GitHub; публикация в GHCR для этого сценария не требуется.

Сборка должна иметь именно текущий origin **`http://10.20.30.45:4007`**, профиль
`legacy-private-lan-http-v1` и `NOT_SECURED=true`. Это явное исключение для уже
согласованного LAN origin. Общий безопасный default для других адресов не ослаблен.
Образ, собранный только для loopback, нельзя исправить заменой runtime environment:
публичные frontend URL входят в сборку.

После нового разрешения на перенос оператор загружает принятый Docker archive на
сервер и выполняет `docker load --input <archive>`; это отдельное изменение Docker.
Далее задаёт в текущем shell только публичные release facts:

```bash
export EDITORIAL_POSTIZ_IMAGE='sha256:<64 hex из принятого proof>'
export EDITORIAL_POSTIZ_ARCHIVE='/private/release/<принятый image archive>'
export EDITORIAL_POSTIZ_ARCHIVE_SHA256='<64 hex SHA именно этого архива>'
export EDITORIAL_NATIVE_ACCEPTANCE='/private/release/acceptance.json'
export EDITORIAL_SOURCE_COMMIT='<40 hex commit из того же принятого proof>'
bash deployment/linux/postiz-release.sh --check
```

Если существующий `TOPIC.md` содержит собственную политику, использовать отдельно
распакованный **полный неизменённый** source ZIP принятого release. Этот каталог
должен находиться вне `/opt/max-postiz`, не содержать symlinks и не получать
приватные настройки VM. Его полный manifest/Git tree проверяется без исключений.
До обновления сохранить SHA исходного `TOPIC.md` из приватного backup/audit; для
проверки сохранённой политики дополнительно задать:

```bash
export EDITORIAL_RELEASE_ROOT='/private/release/<неизменённый каталог принятого source>'
export EDITORIAL_PRESERVED_TOPIC_SHA256='<64 hex исходного TOPIC.md из backup до обновления>'
bash deployment/linux/postiz-release.sh --check
```

В таком режиме все принятые tracked-файлы рабочего `/opt/max-postiz` должны
совпадать с отдельным source побайтно; единственное исключение — **ровно
`TOPIC.md`**, который обязан совпасть с явным исходным SHA. Изменение schema,
кода, scripts, compose, prompts или `config/*.example.json` этим SHA не разрешается.
Без отдельного принятого source исключение недоступно; без исходного SHA
`TOPIC.md` остаётся под обычной точной проверкой. Нельзя пересчитать baseline
после изменения политики лишь ради прохождения guard.

`--check` связывает `accepted=true` / `native_checks_passed=true` в `acceptance.json`
с source commit, полным hash-контекстом сборки и его `portable_image`: ID, SHA/размер
и имя архива, origin/profile, отсутствие runtime credentials и
`startup_contract=postiz-no-implicit-schema-v1`. Проверяется локальный
source manifest (полный SHA-map принятого source) либо то же дерево чистого Git HEAD,
SHA архива, уже загруженный immutable
image ID, origin/profile образа и текущий `POSTIZ_PUBLIC_ORIGIN` в приватном compose env. Затем выполняет
`compose config --quiet`, не печатая подставленные пароли. Это локальная проверка
идентичности; подлинность GitHub run и скачанного proof проверяет владелец. Скрипт
не превращает неподтверждённый run в принятый и не запускает контейнер.
Обязателен нативный `checks.default_cmd_fresh_clone`: успешный owner login и ровно
0 `implicit_schema_statements` в проверенном startup-окне отдельного клона. Hash
`start-production.sh` должен совпасть с фиксированным проверенным script.

**Старый pin нельзя пропустить:** `deployment/linux/compose.yaml` и прежний
`postiz.sh` выбирают образ `0.11.2`. Переменная `POSTIZ_IMAGE` сама по себе этот
последний pin не переопределяет. Новый `postiz-release.sh` добавляет
`deployment/linux/compose.three-platform.yaml` **последним** после четырёх прежних
compose-файлов. Его `image` — полный `EDITORIAL_POSTIZ_IMAGE`, `pull_policy: never`.
Старые файлы и существующие volume bindings не изменены.

Старый унаследованный CMD Postiz содержит `prisma db push`: запуск такого образа
может изменить схему существующей БД. Он **не допускается** к обычному переносу.
Требуется отдельный явно заданный startup без schema push, проверенный в новом
образе и сверенный image guard: пустой `Entrypoint` и точный
`Cmd=["/bin/sh","/adapter/start-production.sh"]`. Старый root `pnpm run pm2`
не используется; новый script явно запускает три проверенных приложения.
Пока эта нативная проверка не принята, `--up`
не является разрешённым шагом и перенос остаётся `NOT_ACCEPTED`.

Только после принятия безопасного startup, проверки паузы/backups и нового
разрешения владельца, а также подготовки host-сервиса по разделу ниже:

```bash
bash deployment/linux/postiz-release.sh --up
```

`--up` допускается только из `/opt/max-postiz`, отклоняет marker изолированной копии
и пересоздаёт только `postiz` с `--no-deps --pull never`. Совместимость существующего
backup и восстановление владелец дополнительно проверяет на отдельном клоне.
Успешный CI с synthetic БД не заменяет эту проверку существующих данных.
Этот helper не запускает редакционный цикл и не подтверждает доступ к площадкам. После запуска независимо
сверить фактический image ID контейнера с принятым ID и HTTP/owner-session проверки.

В handoff overlay `RUN_CRON` пустой и очереди, включая `main,max`, исключены. Это
первый безопасный запуск, а не работающий hourly. Кнопка «Запустить цикл» не меняет
environment контейнера. Возвращение нужных очередей и штатного hourly требует
отдельного решения владельца, точной конфигурации и проверки без догоняющих отправок.

## Редакционный сервис и вход владельца

Перенос приватных конфигураций выполняется адресно с сохранением исходных
настроек, MAX allowlist, binding hashes, политик и истории. Не запускать общий
`activate`/`sync_targets` для повторного создания адресатов. Обычные
`server_cli serve` и `status` проверяют существующую схему без `initialize`,
`activate` и синхронизации адресатов. Миграция — отдельный явный шаг после backup;
она не заполняет БД примерными target и не разрешает отправку.
Source ZIP сначала распаковывается отдельно, а не поверх рабочего каталога.
Собственный `TOPIC.md` сохраняется через отдельный принятый source и явный
проверенный baseline, как описано выше: его не перезаписывают шаблоном.
`config/app.json`, `config/publishing.json` и `.env.local` — приватные runtime-файлы,
а не исключения для всей директории `config/`. Сохранить их исходные SHA вместе с
`TOPIC.md`, deployment env и остальными файлами, на которые ссылается конфигурация,
в приватном audit до обновления; после установки и `--up` проверить те же SHA.
Не выводить содержимое или этот audit в публичные artifacts. Любое непредусмотренное
изменение блокирует завершение переноса; изменение самой политики требует отдельной
аудируемой миграции. Приватные политики не отправляются в CI.

**Обновить нужно и host-сервис, и Postiz.** Docker archive содержит Postiz, но не
Python virtualenv, host Chrome, авторизованные профили или systemd-конфигурацию.
`postiz-release.sh --up` заменяет только контейнер Postiz; он не устанавливает
новые owner API в уже работающий старый Python-процесс. После отдельного разрешения
на перенос выполнить следующий порядок с существующими приватными настройками:

1. Сохранить приватный снимок состояния и backups, убедиться в общей паузе и паузе
   всех адресатов. Дождаться отсутствия активных model/send/mutation claims и
   владельцев; неизвестные исходы сохранить. Только после этого остановить
   **существующий** `max-postiz-editorial.service` на короткое окно обновления.
   Не запускать второй `serve`, старый Hub или desktop worker.
2. Перенести проверенные публичные файлы принятого source в `/opt/max-postiz`
   адресным diff, сохраняя `.env.local`, deployment env, конфигурации, `TOPIC.md`,
   пути профилей, uploads, runtime/journals и права `editorial`. При конфликте
   остановиться и согласовать миграцию; не заменять настройки безопасным примером.
   Сохранить прежний virtualenv/список пакетов для отката. Новый source и wheel
   должны относиться к одному принятому дереву; проверить их manifest/SHA до установки.
3. От пользователя `editorial`, из `/opt/max-postiz`, обновить зависимости Python
   3.12+ по закреплённым lock-файлам и установить именно проверенный wheel. Эти
   команды не запускают сервис, миграцию или публикацию:

   ```bash
   .venv/bin/python -m pip --isolated install --index-url https://pypi.org/simple \
     -r requirements.lock -r requirements-browser.lock -r requirements-deployment.lock
   .venv/bin/python -m pip --isolated install --no-index --no-deps --force-reinstall \
     '/private/release/<проверенный wheel принятого source>'
   .venv/bin/python -m pip check
   .venv/bin/python -c "import importlib.metadata as m, max_postiz_agent as a; print(a.__version__); print(m.version('max-postiz-agent')); print(a.__file__)"
   .venv/bin/python -m max_postiz_agent.server_cli --root /opt/max-postiz status
   ```

   Проверить обе версии и фактический путь импорта. Старый editable install или
   другой интерпретатор не должны незаметно оставить прежнюю реализацию API.
4. `status` проверяет схему без её изменения. Если получен
   `SERVER_MIGRATION_REQUIRED` или `EDITORIAL_MIGRATION_REQUIRED`, сначала проверить необходимые Alembic heads и
   перенос ledger на восстановленном клоне существующей БД. Только после принятия
   этого результата и backup выполнить отдельную миграцию:

   ```bash
   .venv/bin/python -m max_postiz_agent.server_cli --root /opt/max-postiz migrate
   .venv/bin/python -m max_postiz_agent.server_cli --root /opt/max-postiz status
   ```

   `migrate` не синхронизирует адресатов и не включает отправку. Если он отказал
   из-за outstanding/unknown delivery, не очищать её ради установки: сохранить
   результат и остановить перенос до отдельного плана сверки. Ошибка команды не
   доказывает отсутствие уже выполненных изменений схемы: перед любым повтором
   отдельно сверить фактические heads и ledger. Также отдельно
   проверить совместимость **существующей Postiz БД** с новой Prisma-схемой на
   клоне. При необходимости изменения схемы нужен отдельный проверенный план;
   обычный startup не выполняет `db push`.
5. Проверить Linux browser runtime от пользователя `editorial`: закреплённый
   Playwright из `requirements-browser.lock`, установленный Chrome для выбранного
   `channel` либо его фактический `PLAYWRIGHT_BROWSERS_PATH`, доступные этому
   пользователю бинарники, каталог профиля и его владельца. Если используется
   системный Chrome, пользовательский Playwright cache его не заменяет.
   `deployment/linux/install-browser.sh` — отдельная установка при отсутствии
   Chrome: она пишет `max.browser.channel=chrome` и вызывает `try-restart`.
   Применять её только при уже остановленном editorial-сервисе и соответствии
   этого channel переносимой конфигурации. Не переносить Windows cookies и не
   отключать sandbox. Нативный CI доказывает механизм запуска, а не авторизацию
   Linux-аккаунтов владельца.
6. Установить/проверить owner-portal units и активный proxy по порядку ниже,
   выполнить `postiz-release.sh --check` и разрешённый `--up`. После этого запустить
   только фиксированный редакционный сервис и проверить его поколение конфигурации:

   ```bash
   sudo systemctl restart max-postiz-editorial.service
   curl --fail --silent http://127.0.0.1:8092/health
   .venv/bin/python -m max_postiz_agent.server_cli --root /opt/max-postiz status
   ```

   Health должен показывать принятую версию, `interface=postiz_only` и
   `worker_mode=autonomous`; это не разрешение работы цикла. В owner-сеансе Postiz
   сверить настройки/адресатов, сохранённую общую паузу и `restart.required=false`
   в route setup. Сравнить историю, attempts/unknown и отсутствие новых claims
   с исходным снимком. При ошибке версии, schema, generation или bindings не
   включать цикл и не исправлять состояние удалением записей.

Не использовать этот документ как fresh-install рецепт: новый пустой CI стенд
явно получает `publishing.targets=[]` и `tasks=[]` до первой миграции. **При переносе
существующей VM эти массивы и существующие строки не очищаются.**

Для нового изолированного стенда перед первой миграцией также нужен
`data/hourly-article-policy.local.json` из принятого
`config/hourly_article_policy.example.json` с `enabled=false`, правами `0600`
и владельцем `editorial`. Native runner создаёт его эксклюзивно до `migrate`.
Это fixture нового стенда: существующий файл политики VM сохраняется и не
подменяется примером; его изменение требует отдельной аудируемой миграции.

До приёмки проверить зависимости Linux, cgroup delegation, права пользователя
`editorial`, root-owned systemd units и Polkit rule для 7 owner-portal служб/наблюдателей.
Python login/restart helpers работают от `editorial`, а не от root. Установка
проверяется `install-owner-portals.sh --check`; `--install` — отдельный разрешённый
операторский шаг. Не импортировать Python проекта от root в привилегированные helpers.

Установщик owner portal сохраняет nginx-шаблон в
`/etc/max-postiz/editorial-postiz.nginx.conf`, **но не включает его**. Замена образа
через `postiz-release.sh --up` также не обновляет активный публичный proxy. До
проверки панели оператор отдельно применяет proxy-конфигурацию на разрешённой VM:

1. Выполнить `nginx -T` и определить фактические файлы и включения, обслуживающие
   именно `http://10.20.30.45:4007`. Вывод может содержать приватные настройки:
   сохранить его только в локальном файле с правами `0600`, не в CI или публичном
   отчёте. Не предполагать путь active config по имени шаблона.
2. Снять приватную копию всех затрагиваемых файлов вместе с владельцами и правами.
   Сопоставить активный listener с
   `deployment/linux/editorial-postiz.nginx.conf` принятого source. Внести адресный
   diff в существующий server block: owner auth, `/owner-browser/` и точный
   `/api/editorial/route-admin` с лимитом `15m` должны соответствовать шаблону.
   Сохранить остальные listeners и не создавать второй конкурирующий server для
   того же адреса. Для общего файла с несколькими server blocks требуется ручное
   слияние; целиком заменять его шаблоном нельзя.
3. Выполнить `nginx -t`; только при успехе — `systemctl reload nginx`. Проверить
   тот же HTTP origin и owner-session guards. При ошибке конфигурации reload не
   выполнять; при сбое после reload восстановить сохранённые файлы, вновь
   выполнить `nginx -t` и только затем reload прежней конфигурации.

Не запускать старый `network-and-tools.sh` для этой операции: он целиком создаёт
прежний site config и меняет другие системные настройки. Без отдельного применения
и проверки active proxy перенос панели, загрузки изображения и owner portal
не считается завершённым.

В Postiz владелец использует свой cookie-сеанс и выбранный target:

- MAX: выбирать только уже разрешённый numeric ID и имя из allowlist.
- Telegram: вручную ввести токен бота с правами нужного канала. API не возвращает
  токен; пароль браузера таким полем не принимается. Настройки/токен сохраняются на
  паузе, затем применяются фиксированным запросом перезапуска при свободных claims.
- MAX/VK: подготовить вход для конкретного target/binding, открыть закрытое окно
  владельца, вручную войти на Linux и закрыть сеанс. Автовход чужими/Windows cookies
  не предусмотрен; CAPTCHA и ограничения доступа не обходить.

После входа отдельно проверить доступ. Вход в аккаунт не подтверждает доставку и
не делает новый VK target готовым к изображениям: `dom_contract_verified` и
`media_contract_verified` по умолчанию false и не включаются UI checkbox.
Оператор отдельно принимает наблюдённый DOM и привязанные hash/evidence. Выбор
image policy, включая opt-in обработки однотонного края, делается проверенной
конфигурацией; это не общее разрешение crop/resize и не перенос чужой приёмки.

Авторский материал сохраняется без approval. Правка сбрасывает старые проверки и
согласование; нужны полный текст, серверный preview изображения, успешный preflight
и явное человеческое согласование точной версии, адресата и будущей даты. Существующие
политики автоматического MAX не переносятся на Telegram/VK и не включаются миграцией.

При `ROUTE_ADMIN_RECOVERY_REQUIRED` сохранить intent/backups, восстановить доступность
БД и повторить явное действие. Сверка проверяет точные file/DB/audit состояния;
несовпадение оставляет блокировку, а не заменяет данные автоматически. Настройки не
повторяют публикацию и не освобождают чужие claims.

## Приёмка и откат

Сначала принять HTTP/owner auth, настройки, приватность токена, черновик/правку,
preview, CAS и перезапуск на паузе. Затем владелец отдельно согласует конкретный
текст/изображение, адресат и время для одной проверки доставки каждого маршрута.
После отправки — независимая сверка и возврат на паузу. `unknown` не повторяется;
используется только read-only reconcile с сохранением attempts/lease/audit.

Для отката держать проверенный прежний image ID и совместимый source/runtime backup.
Сначала вновь остановить отправку и проверить leases/неизвестные исходы. Прежний
образ выбирать отдельным последним override по сохранённому immutable ID, сохраняя
тот же проект и volumes. Старый tag без проверки ID не является rollback proof.
Новый image guard предназначен для нового release, а не сертифицирует старый образ.

Восстановление БД не автоматизируется этим handoff. После новых записей нельзя
накатывать старый dump поверх живой истории: процедура восстановления и сохранения
новых attempts/unknown должна быть отдельно проверена на клоне и разрешена владельцем.
До этого нельзя объявлять rollback протестированным на production или перенос завершённым.
