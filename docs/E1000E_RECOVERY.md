# Восстановление после зависания e1000e

**Область документа, сверено для 0.11.5 29 октября 2026:** Датированный отчёт сетевого инцидента и процедуры отката. Он не является поручением менять действующую сеть.
Актуальные эксплуатация и состояние: [VM](VM_EDITORIAL.md), [выпуск 0.11.5](RELEASE_0.11.5.md).

18 октября 2026, Europe/Moscow. На Proxmox подтверждён `Detected Hardware
Unit Hang` физического `eno1` с 17 октября 15:43:36 UTC. Хост продолжал
работать, но передача через NIC зависла; 18 октября в 03:18:11 МСК журнал
зафиксировал короткое нажатие Power и начало штатного выключения. Новая загрузка
видна в журнале с 03:19:18 МСК (`uptime -s`: 03:19:16 МСК); VM 109 и 112
запустились автоматически. Это объясняет
одновременную потерю Proxmox, редакционной VM и model-router при доступном
отдельном GPU-сервере. Журнал подтверждает потерю сети при продолжавшей
работу ОС.

Проверенное оборудование: hostname `pve`, ядро `6.8.12-43-pve`, Intel
I219-V `(17)` `8086:1a1d`, PCI `0000:00:1f.6`, driver `e1000e`, firmware
`0.21-4`. Физическая MAC закреплена в guard; сопоставление хранится в
приватном диагностическом снимке. Исходный снимок после загрузки, до меры:
TSO/GSO/GRO и checksums включены; EEE включён, но неактивен;
линк 1 Gbps Full, Wake-on `g`.
Приватные журналы и снимки состояния хранятся только в ignored `data/`.

## Фактическое применение 18 октября

TSO-only применён в 00:31:09 UTC (03:31:09 МСК). Unit
`max-postiz-eno1-tso.service` enabled, active и завершился успешно.
Независимая read-only проверка завершена в 00:31:48 UTC (03:31:48 МСК):
`tcp-segmentation-offload`, `tx-tcp-segmentation` и `tx-tcp6-segmentation`
сменились on → off; GSO/GRO и RX/TX checksums остались прежними.
Линк 1 Gbps Full up; 16 MiB переданы в обоих направлениях с совпадением
SHA-256. В проверенном интервале новых `Hardware Unit Hang` нет;
последующая глубокая проверка стека — 27/27, включая ответы обеих моделей.

Первый общий диагностический запуск завершился ошибкой при чтении
`journalctl` из-за ISO-формата времени, уже после успешного применения.
Повторного apply не было: отдельный read-only helper подтвердил фактические
features и состояние unit. Это различие между ошибкой сбора отчёта и
результатом изменения проверено по сохранённым приватным отчётам.

Для применения не перезагружали хост/VM, не опускали линк и не перезапускали
networking. Следующая загрузка с установленным unit ещё не проверена;
короткая проверка передачи и отсутствие новых ошибок не доказывают
долгосрочную устойчивость. Общий порядок проверки, применения и отката
ниже сохраняется для обслуживания; повторять apply из-за прежней ошибки
сбора журнала не требуется.

## Минимальная мера и её пределы

Intel maintainer рекомендует отключать TSO как обход некоторых зависаний
передачи e1000e при включённом TSO: [первичное обсуждение Intel-wired-lan](https://lists.osuosl.org/pipermail/intel-wired-lan/Week-of-Mon-20190513/016087.html).
Это основание для ограниченной меры, а не доказательство точного дефекта
данного PCI ID или окончательного устранения неисправности.

В upstream Linux 6.8 изменение только TSO/TSO6 не вызывает ветку reset в
[`e1000_set_features`](https://github.com/torvalds/linux/blob/v6.8/drivers/net/ethernet/intel/e1000e/netdev.c#L6820).
Изменение EEE, напротив, явно сбрасывает линк в
[`e1000e_set_eee`](https://github.com/torvalds/linux/blob/v6.8/drivers/net/ethernet/intel/e1000e/ethtool.c#L2129).
Это анализ upstream, не побайтовая проверка всех патчей установленного PVE.
Нулевой риск разрыва удалённого соединения не обещается.

TSO переносит сегментацию TCP с CPU на NIC; GSO и GRO — отдельные механизмы
[сетевого стека Linux](https://docs.kernel.org/networking/segmentation-offloads.html).
Сначала меняется только TSO физического eno1. GSO/GRO, checksums, EEE,
MTU, скорость, autonegotiation, bridge, VLAN, VM, ядро и driver не меняются.
Возможны дополнительная нагрузка CPU и снижение пропускной способности:
оценивать по обычной нагрузке и журналам, а не обещать бесплатный обход.

## Проверка, установка и применение

Сначала сохранить текущие `ethtool -i/-k/--show-eee eno1`, `ip -d link show
eno1`, kernel/PCI и журналы. Убедиться в отсутствии sending/unknown и leases,
сохранить приватную резервную копию заменяемых host-файлов. Не применять
широкие bootstrap/restore, не перезапускать networking или worker.

`deployment/proxmox/guard-eno1-tso.sh` по умолчанию выполняет только `--check`.
Он сверяет hostname, PVE kernel/tools, MAC, точный PCI адрес, vendor/device,
driver через sysfs и ethtool. Несовпадение блокирует применение. `--apply`
требует root, выполняет единственную команду `ethtool -K eno1 tso off`,
проверяет результат и неизменность GSO/GRO/RX/TX checksums. Уже выключенный
TSO повторно не меняется. При ошибке проверки автоматического rollback нет:
сначала прочитать фактические features и журналы, не включать TSO вслепую.

После проверки файлов оператор устанавливает helper как root-owned
`/usr/local/sbin/max-postiz-eno1-tso` с режимом 0755, unit как
`/etc/systemd/system/max-postiz-eno1-tso.service` с режимом 0644. Установка
не встроена в helper и сама по себе не подтверждает применение.

```sh
/usr/local/sbin/max-postiz-eno1-tso --check
systemd-analyze verify /etc/systemd/system/max-postiz-eno1-tso.service
systemctl daemon-reload
systemctl enable --now max-postiz-eno1-tso.service
systemctl is-active max-postiz-eno1-tso.service
ethtool -k eno1
```

Unit [`Type=oneshot`, `RemainAfterExit=yes`](https://www.freedesktop.org/software/systemd/man/latest/systemd.service.html)
применяет меру после появления eno1 и network.target, до pve-guests на
следующей загрузке. JobTimeoutSec=30 ограничивает также ожидание отсутствующего
устройства; TimeoutStartSec=20 отдельно ограничивает выполняемый helper.
При замене NIC или его имени guard не меняет новый адаптер и не должен
неограниченно задерживать запуск гостей. Текущие VM не перезапускаются. ExecStop отсутствует:
остановка unit не должна неожиданно возвращать проблемный TSO. Служба не
восстанавливает настройки после произвольной замены NIC/driver или удаления
устройства; после таких изменений нужна новая проверка. Успешный старт сейчас
не доказывает проверку следующей загрузки или длительную устойчивость.

Не выполнять ifdown/ifup vmbr0: [Proxmox предупреждает о потере гостевой сети](https://pve.proxmox.com/wiki/Network_Configuration).
Для этой меры не требуется даже ifreload, выключение линка или перезагрузка.
После применения проверить SSH/UI Proxmox, VM109/112 и штатный healthcheck;
TSO должен быть off, остальные проверенные features — прежними. Следить за
новыми e1000e hang/reset и счётчиками NIC. Полную перезагрузку для проверки
постоянства проводить отдельно в согласованное окно, не ради текущей проверки.

## Откат

Сначала сверить сохранённый снимок: в этом инциденте прежний TSO был on.

```sh
systemctl disable --now max-postiz-eno1-tso.service
# Только если сохранённый снимок действительно требовал TSO=on:
ethtool -K eno1 tso on
ethtool -k eno1
```

Disable/stop сами по себе TSO не включают. Восстановить прежние helper/unit
из закрытой копии либо удалить только добавленные этим изменением файлы и
выполнить daemon-reload. Не менять остальные features. Откат может вернуть
условия зависания; решение принимается по фактическому состоянию и журналам.
