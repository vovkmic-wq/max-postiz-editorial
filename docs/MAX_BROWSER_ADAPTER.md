# MAX в Postiz через браузер

Версия агента 0.4.1, образ адаптера Postiz 0.4.0 на базе 2.25.1. Схема:
локальная LLM → Postiz: редактор и календарь → агент: согласование → браузер MAX.

## Работа редактора

1. Откройте http://localhost:4007. Выберите подключённый **MAX — браузер**.
   Создайте черновик в Postiz или передайте из панели редакции кнопкой
   «Черновик Postiz»; источники подготовленного агентом варианта сохраняются.
2. Сохраните текст и вложение, назначьте время и поставьте пост в календарь
   Postiz. Для согласования требуется QUEUE. Дата передаётся точно, включая
   миллисекунды; панель не заменяет её округлённым временем.
3. Откройте http://127.0.0.1:8090/hub. Синхронизация выполняется каждые
   15 секунд; доступна кнопка ручной синхронизации.
4. Для текста из Postiz без источников владелец отдельно нажимает
   «Подтвердить авторский текст». Это подтверждение происхождения;
   согласование публикации выполняется отдельно.
5. Проверьте вариант и дату, снимите паузу только нужного адресата и согласуйте
   актуальную версию в агенте. Правка текста, даты, адресата или вложения
   требует нового согласования.
6. В назначенное время агент повторно проверяет Postiz и хеш вложения, затем
   публикует через эксклюзивный прежний браузерный профиль MAX. Postiz остаётся
   pending до проверенного результата. Текущий браузерный транспорт возвращает
   ID операции browser-..., а не native message ID MAX; отдельная ссылка на
   сообщение не извлекается. Unknown требует сверки; автоматического повтора нет.

Не запускайте параллельную отправку из прежнего MAX и этого проекта.
В 0.4.1 выполнена одна согласованная тестовая отправка: 13 октября в 15:21
по Москве. Текст сохранился после reload и новой сессии, Postiz — PUBLISHED.
После теста адресаты снова на паузе. [Отчёт](MAX_TEST_PUBLICATION_REPORT.md).

## Развёртывание

Сначала поднимите PostgreSQL редакции, OpenCode на 4108 и панель на 8090.
Для Docker агент доступен по `host.docker.internal:8090`; связь проверена
с действующей конфигурацией. Для доступа из LAN нужны сетевые ограничения.

Из корня проекта:

```powershell
.\.venv\Scripts\python.exe scripts/configure_max_bridge.py prepare
# На новой машине: собрать overlay либо загрузить сохранённый образ.
docker build -t max-postiz-browser:0.4.0 deployment/postiz-max
.\.venv\Scripts\python.exe scripts/configure_max_bridge.py enable-image
.\scripts\postiz.ps1 check
.\scripts\postiz.ps1 start
# После prepare перезапустите панель, чтобы прочитать новый ключ.
.\.venv\Scripts\python.exe scripts/configure_max_bridge.py connect
```

`prepare` сохраняет общий ключ только в ignored `.env.local` и
`deployment/postiz/.env`. Не копируйте его в отчёты. На новой машине отдельно
авторизуйте браузер MAX: исходный ZIP не переносит cookies и секреты.
Скрипт connect предназначен для max_test и проверяет адресата.
Он сохраняет паузу; включение overlay само по себе ничего не отправляет.

Окончательный образ этой установки получен через закреплённый compiled repair
после первой полной сборки. Повторная чистая сборка актуального Dockerfile
не завершена из-за ресурсов WSL; детали в отчёте. Сохранённый образ находится
в ignored `data/postiz-max-0.4.0-image.tar`:

```powershell
docker load -i data/postiz-max-0.4.0-image.tar
```

Образ не содержит runtime-паролей и не переносит volumes с пользователями,
редакцией и календарём. Volumes Postiz резервируются отдельно от encrypted
backup PostgreSQL редакции.

## Контроль согласования и ошибок

Делегированный `X-Max-Bridge-Key` разрешает connect/exchange/submit/status и
mutation lease; endpoint согласования с ним недоступен. Подписанный токен
связан с адресатом. Перед отправкой проверяются provider, accountId,
disabled/refreshNeeded, QUEUE, дата, хеш текста/настроек и реальные байты медиа.

Nest guard удерживает mutation lease при сохранении/удалении существующего
поста. Во время sending/unknown/published изменение отклоняется. Потерянное
завершение оставляет lease; истечение времени не разрешает отправку.
Владелец может вызвать `POST /api/hub/max-bridge/unlock/{post_id}` с
`confirm_no_request_inflight=true` только после проверки отсутствия запроса,
истечения lease, паузы и отсутствия sending/unknown. Затем нужна синхронизация.

## Ограничения

- Один пост, не более одного PNG/JPEG/WebP/MP4 из локального Postiz
  `/uploads/`, не более 100 MiB. Threads и recurrence отклоняются.
- Штатный Postiz проверяет pending около 30 минут после даты. Если approval
  не было вовремя, расследуйте результат и назначьте новую дату;
  повторять отправку вслепую нельзя.
- Overlay закреплён под 2.25.1. Другая версия требует переноса и тестов;
  проверки SHA-256 намеренно отклоняют неподходящую базу.
- Пикабу — ручной экспорт; Telegram/VK выключены. Общий
  `approval_guard_verified=false` не меняется: MAX защищён своим мостом,
  обычные маршруты Postiz этим адаптером не защищены.
