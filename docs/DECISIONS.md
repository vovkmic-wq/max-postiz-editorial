# Решения
1. Самостоятельный пакет на основе реального MAX, без переписывания исходного проекта.
2. PostgreSQL — штатная БД. SQLite — явный development режим для переноса и быстрых тестов.
3. В начальном охвате MAX и Пикабу, прежние адресаты; Telegram/VK отключены.
4. MAX browser сохранён: действующий токен Bot API не найден. Vezdepost не может наследовать эту авторизацию.
5. Пикабу публикуется вручную по проверенному контракту предыдущего агента.
6. Канонический Draft и отдельные Variant/Approval/Dispatch позволяют править площадки независимо.
7. При неопределённом внешнем эффекте — остановка и сверка, без обещания exactly-once.
8. Postiz выбран как документированный REST-контракт, deployment взят из canonical repo. Vezdepost рассматривается после подтверждения конкретного fork runtime.
9. Native Postiz approval guard не реализуется одним флагом. Публикация через Postiz закрыта до реальной проверки restrictions.
10. Исходники/зашифрованное состояние/секреты/браузер переносятся раздельно.
11. Нейровидео и image model не входят в доказательство текстовой связки; legacy media-модули сохранены, новые нейронные генерации не заявляются.
12. Локальная LLM не заменяется облаком при недоступности. Реальная генерация остаётся отдельным незавершённым gate.
13. Старый автономный image scheduler MAX и его HTTP-включение закрыты в Hub. Оба console entrypoint ведут в hub_cli; согласование платформенного варианта обязательно.
