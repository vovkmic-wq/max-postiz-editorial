# Диагностика недоступности серверов

18 октября 2026, Europe/Moscow. Диагностический скрипт, добавленный в 0.6.6,
запускается на рабочем компьютере и не требует работающей редакционной VM:

```powershell
.\.venv\Scripts\python.exe scripts/check-network.py --output data/network-check.local.json
```

Он проверяет TCP-подключения к Proxmox, редакционной VM, общему API LLM,
отдельному GPU-серверу и шлюзу. Код 0 означает доступность всех основных
проверяемых TCP-портов выбранного пути; это не проверка входа, генерации модели,
состояния контейнеров или доставки в MAX. Код 1 означает сетевую недоступность
хотя бы одного основного порта. Сохраняемый JSON должен находиться внутри
игнорируемого каталога data/. Пароли, ключи и cookies скрипт не читает.

Для проверки прямого пути Windows через конкретный интерфейс:

```powershell
Get-NetIPConfiguration
.\.venv\Scripts\python.exe scripts/check-network.py --interface-index 3 --source-ip 10.20.30.94 --output data/network-wifi.local.json
```

Номер интерфейса и исходный адрес берут из текущей конфигурации компьютера;
значения примера относятся к диагностике 18 октября. Скрипт сохраняет также
обычный проход для сравнения. IP_UNICAST_IF выбирает интерфейс только для
своего сокета. Системные маршруты, VPN, firewall, службы и питание он не меняет;
SSH-команды, публикации и Wake-on-LAN не выполняет.
Назначение IP_UNICAST_IF описано в
[документации Microsoft](https://learn.microsoft.com/en-us/windows/win32/winsock/ipproto-ip-socket-options).

## Наблюдения до восстановления, 17–18 октября

Следующие результаты описывают период недоступности до новой загрузки хоста.
Подтверждённое текущее состояние и результат разбора журналов приведены ниже.

- С 17 октября около 18:44 МСК подключения к Proxmox 10.20.30.142,
  редакционной VM 10.20.30.45 и model-router 10.20.30.95 перестали отвечать.
  Последние две подтверждённые публикации были завершены до сбоя.
- На ноутбуке одновременно существовали маршруты 10.20.30.0/24 через Wi-Fi
  и WireGuard remote-laptop. Обычным выбором Windows был WireGuard:
  route metric 0 + interface metric 5 против 256 + 35 у Wi-Fi.
  Это конкуренция маршрутов, но сама по себе она не доказывает отказ VPN.
- 18 октября в 02:36–02:43 МСК SSH физического GPU-сервера 10.20.30.143
  отвечал через оба интерфейса. Вход существующим ограниченным ключом прошёл
  с проверкой закреплённого host key; штатный read-only worker status успешен.
  Прямой health Ministral на порту 8086 вернул HTTP 200 и status=ok.
  Общее API на прежнем адресе 10.20.30.95:8083 тогда оставалось недоступным.
- Proxmox, редакционная VM и model-router не отвечали через оба пути.
  В таблице соседей Wi-Fi адрес Proxmox был Unreachable без разрешённого MAC,
  тогда как GPU-сервер и Keenetic имели действующие записи.
- Однократная проверка портов 22 и 8006 в серверной подсети через Wi-Fi
  обнаружила только SSH GPU-сервера. Новый доступный адрес Proxmox или VM
  этой проверкой не найден. Шлюз 10.20.30.254 открыл Keenetic Sprinter SE;
  на этом этапе административная сессия ещё не была открыта. Последующий
  вход владельца описан в следующем разделе.

Эти наблюдения сужали область отказа до Proxmox или его подключения к сети.
Питание, зависание NIC, кабель/порт и отдельный сетевой сегмент тогда
оставались гипотезами. Работоспособный GPU через оба пути не давал оснований
приписывать весь инцидент клиентскому VPN. Причину уточнили журналы Proxmox
после восстановления доступа.

## Историческая проверка Keenetic 18 октября

Владелец предоставил существующий административный доступ к маршрутизатору.
Вход прошёл; пароль не включён в исходники, журнал версий или отчёты.
Контроллер Keenetic имеет uptime более 13 суток, mesh-ретранслятор также
доступен. Роутер и его LAN не перезагружались при восстановлении.

Сохранён и разобран системный журнал Keenetic: последняя DHCP-аренда
редакционной VM продлена 17 октября в 18:21:52, VM моделей — в 17:05:47.
Событий физического LAN link down/up в окне 18:30–19:05 нет. Отсутствие таких
записей не доказывает исправность кабеля и не устанавливает причину отказа.
Проверка ping с самого Keenetic получила Host unreachable от маршрутизатора:
5 запросов, 0 ответов. Это независимая от ноутбука и его VPN проверка.

Физический MAC Proxmox найден в четырёх прежних сетевых наблюдениях
29 сентября — 8 октября: Windows ARP, таблица клиентов Keenetic и ARP из VM
с тем же IP и Debian SSH. Точное соответствие и источники сохранены только
в ignored data/proxmox-wol-mac-evidence-20261018.local.json. Это историческая
привязка: замена NIC после последнего наблюдения отдельно не подтверждена.
MAC старого OpenMediaVault и виртуальные MAC гостевых машин не использовались.

В 03:10:35 МСК отправлен один WOL-пакет по прямому Wi-Fi пути. В 03:15:17
выполнена отдельная отправка из самого Keenetic штатной командой
ip hotspot wake для подтверждённого MAC. Маршрутизатор вернул WoL sent to host.
Эта команда [не меняет постоянную конфигурацию](https://archive.keenetic.ru/files/cli_manual_keenetic_iii.pdf)
(раздел ip hotspot wake). Ответ об отправке пакета не подтверждает включение
компьютера: требуются поддержка WOL, дежурное питание, настройка BIOS/NIC
и исправный сетевой путь. Эти условия описаны в
[инструкции Keenetic](https://support.keenetic.com/orbiter-pro/kn-2810/en/14192-waking-up-a-device-over-the-network--wake-on-lan-.html).

На проверках непосредственно после этих отправок Proxmox и его VM ещё
оставались недоступны. Поэтому владелец получил инструкцию проверить питание/кабель и выполнить
штатное выключение коротким Power; принудительное выключение допустимо
лишь при зависании, с риском потери незаписанных данных VM. Физическая
перезагрузка на этом этапе ещё не была подтверждена новой загрузкой хоста.
Последующие журналы, описанные ниже, подтвердили, что во время отправок WOL
ОС продолжала работать. Публикации и повторная подготовка при недоступной VM
не запускались.

## Подтверждённое восстановление и причина

После появления SSH прочитан журнал предыдущей загрузки. С 17 октября
15:43:36 UTC, то есть 18:43:36 МСК, `e1000e` сообщал `Detected Hardware
Unit Hang` физического eno1. Ошибка повторялась примерно каждые две секунды
до 18 октября 03:18:10 МСК. ОС продолжала исполнять cron как минимум до
03:17 МСК: пропала сеть хоста и его гостей при работающем компьютере.

18 октября в 03:18:11 МСК зафиксированы короткое нажатие Power и начало
штатного выключения. Следующая загрузка подтверждена журналом с 03:19:18 МСК;
`uptime -s` показывает начало работы 03:19:16 МСК. VM 109 и 112 запустились
автоматически. Повторная глубокая проверка стека завершилась успешно:
27 из 27 проверок, включая реальные ответы обеих моделей.

Отдельная сверка БД, Postiz и фактического MAX подтвердила две прежние
публикации: оба точных текста видны по одному разу, соответствующие dispatch
имеют verified, Postiz — PUBLISHED. Третья подготовка из истёкшего часа после
сверки штатно закрыта через `abandon-prepared` со статусом cancelled;
внешних привязок и отправки у неё нет. Активных dispatch и mutation
leases — ноль, все адресаты на паузе. Полные отчёты и идентификаторы находятся
только в ignored data/; во время восстановления новых постов не создавали.

Подтверждено зависание сетевого адаптера e1000e; конкретный механизм,
вызвавший его на этой модели NIC, пока не установлен. 18 октября в
00:31:09 UTC (03:31:09 МСК) применена ограниченная мера TSO-only; unit
enabled, active и завершился успешно. Отдельная read-only проверка завершена
в 00:31:48 UTC (03:31:48 МСК): изменились только TSO и связанные TCP/TCP6
segmentation flags on → off, GSO/GRO и checksums сохранены, линк 1 Gbps Full
up. Передача 16 MiB в каждом направлении проверена совпадением SHA-256;
в проверенном интервале новых Hardware Unit Hang нет. После меры deep-check
снова прошёл 27 из 27 проверок. Подробности и порядок отката приведены в
[E1000E_RECOVERY.md](E1000E_RECOVERY.md).

Общий запуск диагностики сначала остановился на формате времени для
`journalctl`, когда изменение уже было выполнено; применение вслепую не
повторяли, фактическое состояние прочитали отдельной проверкой. Для меры
хост, сеть и VM не перезагружались. Следующая загрузка с этим unit и
долгосрочная устойчивость ещё не проверены; текущие результаты не доказывают
окончательное устранение неисправности.

## Дальнейшие действия

1. Сохранить закрытые копии исходных журналов, снимков NIC и результатов
   сверки. Не перезагружать работающий хост или гостей ради повторной проверки.
2. Наблюдать новые e1000e hang/reset, NIC counters и обычную нагрузку CPU/сети.
   Не менять VPN, EEE, GSO/GRO, checksums или bridge одновременно с этой
   мерой. Проверку следующей загрузки проводить отдельно в согласованное окно;
   успешный unit сейчас не заменяет её.
3. Истёкшая подготовка уже закрыта. При будущем аналогичном восстановлении
   сначала сверять внешние действия, затем использовать abandon-prepared;
   для подготовки без Draft/Variant и внешних действий — cancel-preparation.
   Источник, использованный час и история сохраняются; журнал и RemoteDraft
   вручную не удаляют.
4. Продолжать только с новой допустимой статьёй и новым часовым слотом после
   проверки минимального интервала. Unknown/sending не отправляют повторно,
   пропущенные часы не догоняют. После завершённой проверки max_test остаётся
   на паузе. Порядок проверки автозапуска: [STARTUP_AND_HEALTH.md](STARTUP_AND_HEALTH.md).

## Дополнение 22 октября 2026: диагностика после миграции 0.7.0

Этот раздел описывает новый порядок; наблюдения 17–18 октября выше сохранены
как история. После переключения единственная внешняя панель —
[Postiz](http://10.20.30.45:4007/), раздел «Редакция». Старые Hub-порты
8090/8091 выводятся из эксплуатации. Их недоступность не означает отказ сети
и не является поводом включать прежний worker.

`scripts/check-network.py` больше не обращается к этим двум портам. Он по-прежнему
проверяет публичный Postiz на порту 4007, SSH редакционной VM, Proxmox, LLM-router и GPU,
не выполняя вход, генерацию, перезапуск или публикацию. Отказ Postiz на порту 4007 остаётся
ошибкой обязательной TCP-проверки; внутренний API на порту 8092 не требуется открывать
рабочему компьютеру.

```powershell
.\.venv\Scripts\python.exe scripts/check-network.py --output data/network-check.local.json
```

Для проверки самой редакции внутри VM используют новый сервис и его локальный
health endpoint:

```sh
systemctl is-enabled max-postiz-editorial.service
systemctl is-active max-postiz-editorial.service
curl --fail --silent --show-error http://127.0.0.1:8092/health
```

Эти результаты не подтверждают обработку моделей, действительность MAX-сессии
или доставку текста. Сначала сверяют прежние dispatch, sending/unknown, mutation
leases, Postiz и фактический MAX; неизвестную отправку не повторяют, часы не
догоняют. Журнал и резервные копии сохраняют. При восстановлении не запускают
старый Hub рядом с `max-postiz-editorial.service`. Порядок переключения и границы
проверок: [VM_EDITORIAL.md](VM_EDITORIAL.md).
