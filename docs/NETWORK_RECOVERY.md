# Диагностика недоступности серверов

18 октября 2026, Europe/Moscow. Диагностический скрипт версии 0.6.6
запускается на рабочем компьютере и не требует работающей редакционной VM:

```powershell
.\.venv\Scripts\python.exe scripts/check-network.py --output data/network-check.local.json
```

Он проверяет TCP-подключения к Proxmox, редакционной VM, общему API LLM,
отдельному GPU-серверу и шлюзу. Код 0 означает доступность всех основных
проверяемых TCP-портов выбранного пути; это не проверка входа, генерации модели,
состояния контейнеров или доставки в MAX. Код 1 означает сетевую недоступность
хотя бы одного основного порта. Сохраняемый JSON должен находиться внутри
игнорируемого каталога data/. Пароли, ключи и cookies скрипт не читает.

Для проверки прямого пути Windows через конкретный интерфейс:

```powershell
Get-NetIPConfiguration
.\.venv\Scripts\python.exe scripts/check-network.py --interface-index 3 --source-ip 10.20.30.94 --output data/network-wifi.local.json
```

Номер интерфейса и исходный адрес берут из текущей конфигурации компьютера;
значения примера относятся к диагностике 18 октября. Скрипт сохраняет также
обычный проход для сравнения. IP_UNICAST_IF выбирает интерфейс только для
своего сокета. Системные маршруты, VPN, firewall, службы и питание он не меняет;
SSH-команды, публикации и Wake-on-LAN не выполняет.
Назначение IP_UNICAST_IF описано в
[документации Microsoft](https://learn.microsoft.com/en-us/windows/win32/winsock/ipproto-ip-socket-options).

## Установленные факты инцидента 17–18 октября

- С 17 октября около 18:44 МСК подключения к Proxmox 10.20.30.142,
  редакционной VM 10.20.30.45 и model-router 10.20.30.95 перестали отвечать.
  Последние две подтверждённые публикации были завершены до сбоя.
- На ноутбуке одновременно существуют маршруты 10.20.30.0/24 через Wi-Fi
  и WireGuard remote-laptop. Обычный выбор Windows — WireGuard:
  route metric 0 + interface metric 5 против 256 + 35 у Wi-Fi.
  Это конкуренция маршрутов, но сама по себе она не доказывает отказ VPN.
- 18 октября в 02:36–02:43 МСК SSH физического GPU-сервера 10.20.30.143
  отвечал через оба интерфейса. Вход существующим ограниченным ключом прошёл
  с проверкой закреплённого host key; штатный read-only worker status успешен.
  Прямой health Ministral на порту 8086 вернул HTTP 200 и status=ok.
  Общее API на прежнем адресе 10.20.30.95:8083 остаётся недоступным.
- Proxmox, редакционная VM и model-router не отвечали через оба пути.
  В таблице соседей Wi-Fi адрес Proxmox был Unreachable без разрешённого MAC,
  тогда как GPU-сервер и Keenetic имели действующие записи.
- Однократная проверка портов 22 и 8006 в серверной подсети через Wi-Fi
  обнаружила только SSH GPU-сервера. Новый доступный адрес Proxmox или VM
  этой проверкой не найден. Шлюз 10.20.30.254 открывает Keenetic Sprinter SE;
  административная веб-сессия отсутствует.

Наблюдения локализуют отказ на физическом Proxmox или его подключении к сети.
Выключенное питание, зависание, отказ NIC/кабеля/порта и проблема отдельного
сетевого сегмента остаются гипотезами. Без состояния порта/питания и журналов
Proxmox точную первопричину установить нельзя. Работоспособный GPU и VPN
не позволяют приписывать весь инцидент клиентскому VPN. Изменение его
приоритета не восстановит сервер, отсутствующий и на прямом пути.

## Продолжение восстановления

1. Войти в существующий Keenetic владельца, проверить устройство Proxmox,
   его физический MAC, DHCP/ARP и состояние Ethernet-порта. Сохранить сведения
   только в data/. Не использовать MAC виртуальной сетевой карты VM для WOL
   физического сервера. Доступ к маршрутизатору и физический MAC сейчас
   не сохранены в проекте; без них удалённое включение не выполнено.
2. Если подтверждены физический MAC и поддержка WOL, направить один magic
   packet через доступную локальную сеть/маршрутизатор и проверить загрузку.
   Если аппаратного способа управления нет, требуется проверка питания,
   кабеля и консоли сервера на месте. Не отключать работающие VPN и firewall
   ради неподтверждённой причины.
3. После появления Proxmox сначала прочитать uptime, историю загрузок,
   system/network/kernel journals около 17 октября 15:30–16:05 UTC,
   состояние физических NIC/bridge, storage и pve-guests. Не перезагружать
   хост вслепую: это может уничтожить диагностический контекст и прервать VM.
   Для файловых систем, питания и аппаратных ошибок нужны фактические журналы.
4. Проверить VM 109 и 112, их адреса и штатный автозапуск по
   [STARTUP_AND_HEALTH.md](STARTUP_AND_HEALTH.md). Затем выполнить
   scripts/check-startup.ps1 -Deep и отдельно сверить MAX/Postiz.

Перед новой статьёй требуется сверка сохранённой прерванной подготовки
через scripts/hourly_article_test.py status, БД dispatch/mutation leases,
Postiz и фактический MAX. Истёкший локальный prepared без внешних действий
закрывают штатным abandon-prepared; неудачную подготовку без вариантов —
cancel-preparation. Источник и использованный час остаются в журнале.
Unknown/sending не отправляют повторно. Пропущенные часы не догоняют,
max_test после завершённой проверки должен оставаться на паузе.

Приватные сетевые отчёты и идентификатор подготовки находятся в ignored data/.
Текущий сетевой сбой не даёт возможности подтвердить итог этой подготовки,
состояние runtime VM или новые публикации. Диагностика рабочего компьютера
не является восстановлением Proxmox и не подтверждает живую интеграцию.
