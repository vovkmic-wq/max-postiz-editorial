### Новый формат и неизменяемые доказательства

Формат включается отдельной политикой `article-illustrated-v1` и точным
поручением владельца. Полные текстовые подписи и оригинальные изображения
проверяются только в разрешённых разделах NOIRLab IOTW и ESA/Hubble POTW.
Для изображения сохраняются условия CC BY 4.0, credit со ссылками, точный URL,
исходный JPEG, размеры и SHA. Официальный wallpaper 2048×1536 предпочтительнее
тяжёлого печатного JPEG; минимум — 1600×800 с учётом длинной/короткой стороны.
Файл не подменяется иллюстрацией с непроверенными правами, EXIF-поворот не
игнорируется. У NASA нет автоматического разрешения на любые изображения.

Первая реализация 0.11.0 использовала ограниченный HTTP Range: 8192 байта, не более двух одновременных
запросов и 512 диапазонов, с точными Content-Range/ETag/If-Match. Каждый диапазон
получает durable claim до GET, затем проверяется длина и SHA блока. Ответ 200
допустим как полный файл только на первый запрос. Потерянный claim, изменённый
ETag, неверный диапазон, таймаут и 401/403/429 не разрешают повтор или обход.
Наличие корректного полного proof позволяет только локальный replay без GET.

Изображение, его доказательство прав, credit и формат входят в record,
machine evidence, историю variant и точный approval snapshot. Статья сначала
получает проверенное изображение, затем MADLAD/Ministral/LanguageTool. После
содержательного отказа допустимы две адресные Qwen-правки с новой независимой
проверкой каждого изменённого кандидата. Полный оригинал, raw и отказы остаются.

Новый пост должен показывать изображение перед текстом; только заголовок
выделяется встроенным жирным начертанием MAX, тело остаётся обычным текстом.
Символы Markdown `**` в публикацию не добавляются. Браузер проверяет точный
текст, формат заголовка и вложение до Send и после подтверждения доставки.
Подпись сохраняет источник, лицензию и полный credit, а изменения обозначены
нейтрально: «Перевод и адаптация.». Старый машинный footer остаётся только
в исторических версиях. Без проверенного изображения новый формат не публикует
один текст; новые настройки не переписывают прошлые записи и unknown.

### Резерв, источник и обслуживание

Подготовка и отправка независимы: один systemd-сервис держит раздельные потоки
пополнения и отправителя с PostgreSQL fencing. Цель запаса — 6, пополнение при 3,
максимум 12, до трёх новых источников за проход. Отправка возможна только после
точного назначения даты, с фактическим интервалом не менее 3600 секунд и без
догоняющих пачек. `sending/unknown`, leases и неизвестный upload требуют сверки.

Корпус конечен: до нового поручения возраст источника ограничивался 8760 часами, а длина,
права и дедупликация по всей истории дополнительно сужают выбор. `no_source`
не снимают восстановлением отменённых статей, сокращением оригинала, повтором
отказа или неподтверждённым расширением прав. Целевые шесть — настройка запаса,
а не доказательство непрерывного снабжения материалами.

Для установки сначала проверяют код и isolated PostgreSQL/fakes, сохраняют
закрытые backup обеих БД, runtime, конфигурации и старого образа. Пользовательская
панель остаётся Postiz `/editorial` на закрытом origin 4007; API 8092 обслуживает
только внутренний BFF и провайдер. API не останавливают на время долгой QA,
сборки или backup. При будущем QUEUE сначала сверяют exact версию и due;
короткий перезапуск допускается с достаточным запасом и проверкой здоровья.
Старт/паузу выполняют штатно из Postiz, второй worker или desktop heartbeat
не включают. Перенос из Git требует отдельных приватных credentials, cookies,
БД и Docker volumes; исходный архив содержит правила, промпты и CHANGELOG,
но не эти данные. Установка и новая фактическая доставка фиксируются отдельно.

Понятные буквальные обороты, неровный стиль, варианты имён, отдельные ошибки

это различие; `approved=true` вместе с непустыми `issues` невалиден. Числа,
ссылки, русский язык, права, все exact bindings, неизвестные исходы,
дедупликация и фактический интервал 3600 секунд остаются обязательными.

хранит микросекунды. В 0.10.7 неизменная native-дата используется для binding,
интервала и аудита, а наблюдаемый GET сравнивается с допуском менее 1 мс.
Другие даты, невалидный ответ, lease и неизвестный исход по-прежнему блокируют.
Это не разрешает новую отправку, approval или перепланирование старого QUEUE.

## Проверка и восстановление 28 октября 2026

Установленная 0.10.7 прошла 1885 изолированных тестов в 42 модулях без ошибок
и пропусков. QA использует отдельную PostgreSQL и fakes. Во время проверки
37 production-таблиц с 108 записями и 254 core/runtime файла остались точными;
известный pending был исключением только для чтения, без права отправки.
После backup обеих БД заменены ровно шесть публичных файлов, source и metadata
согласованы, миграция схемы не выполнялась. Приватная конфигурация, модели БД,
история и назначенный слот сохранены; установка не возобновляла цикл.

Последняя доставка перед перерывом подтверждена в 10:10:50 МСК. Во время
остановки агента для обслуживания Postiz в 11:37–11:40 МСК записал
`MAX_BROWSER_AGENT_UNAVAILABLE`. При запуске sync в 11:51:13 МСК впервые
наблюдал ERROR и отменил dispatch с отзывом approval. Отправок у этого задания
не было, но pending-слот остался активным со старой control revision. Он
блокировал назначение следующей статьи, хотя в запасе были готовые переводы.
Время перехода Postiz в ERROR не установлено: время импорта не выдаётся за него.

Общая пауза агента не останавливает уже назначенную очередь Postiz. При будущем
QUEUE API агента должен оставаться доступным: сначала дождаться и сверить
фактическую отправку либо согласованно остановить отдельный provider worker
с проверкой внешнего исхода. Одна проверка paused в агенте недостаточна для
безопасного отключения сервиса, к которому затем обратится Postiz.

Для этого единственного просроченного слота выполнен адресный протокол:
общая пауза 62, сервис остановлен, свежий GET того же Postiz ERROR, точные
текст/дата/привязки, отозванное согласование, отменённый dispatch с нулём
attempts, отсутствие leases и browser receipt. До изменения сохранён закрытый
снимок всех таблиц и одноразовый claim. Транзакция изменила только слот на
`missed`, сняла `active_target` и добавила Audit. Все 108 records и остальные
35 таблиц сохранены точно. Отменённая статья остаётся использованной навсегда;
её dispatch, approval и Postiz ERROR не восстанавливались. Этот протокол
не распространяется на sending/unknown или возможную прежнюю доставку.
Автоматический переход sending/unknown в missed не добавлен; зависший слот
освобождён одноразово по сохранённым доказательствам известной неотправки.

После проверки запущен единственный серверный сервис и выполнен штатный
start 62→63. Следующая новая статья фактически доставлена в 15:12:42 МСК:
одна published-попытка, Postiz PUBLISHED, точная сверка текста, согласования,
даты и quality evidence. Автоправок у кандидата не было, Ministral и hard gates
пройдены, пять замечаний LT сохранены как advice практичной рубрики. Полный
текст независимо прочитан в MAX дважды: ровно один экземпляр и точное
совпадение в обеих проверках, без внешних мутаций. Это одиннадцатая новая
доставка после активации практичной рубрики. Перерыв 10:10–15:12 сохраняется
в истории и не выдаётся за непрерывную почасовую работу.

Следующий точный pending назначен на 16:12:43 МСК, ещё четыре записи
quality_ready. Догоняющих отправок нет; интервал следующей доставки сохраняет
нижнюю границу 3600 секунд. Подробные receipts и снимки хранятся только в
игнорируемых локальных файлах. В 0.10.7 аналогичный известный сбой пока требует
адресной сверки: автоматическое освобождение такого слота не реализовано.

## Состояние и управление

Контракт новых исправлений article-repair-v8 отделяет необязательные либо
ошибочные предупреждения Ministral от реальных ошибок LanguageTool и полного
EN/RU. Частично ошибочная критика не оправдывает отказ исправлять другие
ошибки. Допустима грамотная русская формулировка с тем же точным смыслом;
факты и все hard gates сохраняются. Формы ответа и строгий Latin guard
совпадают с V7. Сохранённые V3–V7 воспроизводятся прежними промптами;
старые отказы и отменённые записи новым промптом редактора не пересматриваются.

`max-postiz-editorial.service` запускает один процесс с единственным отправителем
и отдельным потоком подготовки. Режим резерва включается явной настройкой после
миграции 0008; до этого сохраняется прежнее ограничение одной подготовки в час.
Сессионная advisory lock PostgreSQL исключает второго владельца, а проверка
владения перед мутациями запрещает продолжать работу после потери соединения.
Проверенный резерв доставляется независимо от долгой подготовки моделей.
Нет общего `tick`, догоняющих пачек или повторов неизвестного HTTP.
В open_science каждый следующий кандидат резерва начинает подбор со следующего
разрешённого источника после предыдущей записи резерва: известный отказ одного
источника не задерживает проверку других до конца часа. Начальный подбор и
прежний режим без резерва сохраняют приоритет по часу. Неизвестный model claim
по-прежнему останавливает новую подготовку до сверки.

Новые автоматические тексты переводит исправленный MADLAD causal-v2. Известный
отказ качества до DRAFT исправляет отдельный Qwen35-9B, после чего требуются
новые независимые Ministral и LanguageTool. В режиме резерва кандидат остаётся
локальным quality_ready до назначения точного слота отправителем.
Редактор получает полный оригинал, прежний перевод и исходные замечания;
возвращает точные проверяемые замены либо честный отказ от исправления.
Его ответ не является согласованием. После двух неудачных содержательных
исправлений запись сохраняет отказ. В режиме резерва сразу выбирается другой
источник в пределах бюджета; прежние записи сохраняют историческое правило часа.
То же происходит, если безопасной правки нет или предложен прежний текст.
Полностью полученный невалидный ответ редактора изолируется без повторного
запроса: отдельный Audit и исходный raw доказывают протокольный отказ, исходная
статья остаётся отклонённой. В режиме резерва после доказанного завершённого
отказа выбирается другой источник без повторения прежнего. Это не отказ Ministral
и не одобрение перевода. Повреждение доказательства
карантина блокирует закрытие. Инфраструктурная ошибка, неизвестный запрос,
незавершённый/потерянный claim требуют сверки и останавливают новую подготовку.
Готовый запас может отправляться независимо от неизвестной модели только при
отсутствии неизвестных внешних операций и leases адресата.
[Полный порядок резерва и восстановления](HOURLY_RESERVE_PLAN.md).

Размер фрагмента MADLAD можно явно задать через `segment_chars` в локальном
`config/translation.json`: целое число от 400 до 1400, прежнее значение 1400
сохраняется при отсутствии поля. Бюджет 600 использует прежнее разбиение по
абзацам и границам предложений; длинное предложение делится по пробелу без
обрезания остатка. Контекст не дублируется, разметка в модель не добавляется.
Другим переводчикам изменение бюджета не разрешено. Новый режим сохраняет
контракт сегментации, порядок, размеры, input/output hashes и worker evidence
в `translation_returned`; весь собранный текст проходит прежние hard gates,
независимый Ministral и LanguageTool. Изменение размера не пересэмплирует
отклонённые статьи и не отменяет два durable claim редактора.

Перекрывающиеся окна в `translation_chunks.py` — отдельный эксперимент,
не подключённый к production factory. Одна живая проба ASCII-маркеров
27 октября завершилась повторением разметки до лимита 1024 tokens
(`complete=false`, 248,91 секунды); её полный raw сохранён локально.
Автоматической склейки по похожести текста и переключения после отказа нет.
На замороженном корпусе перекрытие увеличивало объём входа в 1,72 раза;
это не доказательство улучшения качества или скорости. Бюджет 600 включается
отдельным аудируемым решением на безопасной паузе после проверки полной статьи.

Новые исправления используют article-repair-v7: смешанная кириллица с латинской
буквой внутри слова (например, «Хорáлек») блокируется до Min/LT. Старые V3–V6
сохраняют прежние prompt/hash/replay для аудита; их сохранённые ответы не
превращаются в новые исправления. Лимит двух claims и запрет повтора прежние.

Для session-запросов OpenCode приватный журнал `data/opencode-requests/` сохраняет
intent/prompt hash до сети, session ID до generate и HTTP response bytes до
разбора. При timeout, HTTP/JSON/empty/disk failure session не прерывается и не
удаляется автоматически: результат нужно сверить через GET существующей сессии,
без нового generate. Обычная очистка допустима после сохранённого валидного
ответа. Файлы журнала не входят в архив исходников и могут содержать приватный текст.
Ранее удалённая сессия без точной связи с запросом остаётся unknown: отсутствие
сессии и временная корреляция логов не заменяют полный результат и не разрешают
повтор либо протокольный карантин.

Такой же карантин применяется к полному ответу редактора, потерявшему исходную
ссылку: строгий валидатор повторно проверяет сохранённый raw без нового запроса
модели. Прежний известный `failed` с `TRANSLATION_REFERENCE_CHANGED` можно
адресно закрыть только `AutomaticArticleRepair.quarantine_failed_reference`
на общей паузе с явной причиной. Одноразовый Audit сохраняет полный прежний
claim; DRAFT, согласование, отправка и повторная оценка текста не создаются.

Полный известный отказ редактора с изменённым числом обрабатывается так же:
`AutomaticArticleRepair.quarantine_failed_number` на общей паузе повторно
подтверждает точную числовую ошибку по сохранённому raw и сохраняет старый failed.
Это отказный карантин, а не исправление или одобрение текста.

Новые редакторские ответы используют `article-repair-v6`: редактор дополнительно
получает точные списки исходных, пропущенных и посторонних URL. Числа внутри
ссылок восстанавливаются только вместе с целым исходным URL. Код не дописывает
потерянные ссылки и не исправляет текст за редактора. Неизменённый ответ
по-прежнему завершает попытку отказом без нового запроса Ministral.

Как и в v4, безопасные HTTP(S)
Markdown-ссылки приводятся к тому же обычному тексту, что и исходный перевод.
Далее без изменений выполняются diff, защита от повтора, числа, полнота ссылок,
новые Ministral и LanguageTool. Форматирование само по себе не снимает отказ.
Исторические v3, v4 и v5 сохраняют свои прежние промпты и контекст; v3 переигрывается
только старым строгим валидатором. Новая диагностика применяется к будущим
попыткам и не разрешает пересэмплировать старые отказы.

Будущая проверка `article-links-v2` сохраняет весь literal URL, включая внутренние
скобки, query, fragment и percent encoding. Версия и полные списки исходных
и русских ссылок связаны с trace и машинным доказательством. Marker записывается
до перевода в record, attempt и Audit: удаление нового поля не превращает такую
проверку в исторический v1. Старые доказательства читаются по прежним правилам,
но перед любой будущей отправкой дополнительно проверяются полные URL по v2.
Канонизация Markdown и hashes дедупликации остаются `article-links-v1`: это
отдельный формат текста, который уже сохраняет скобки и не требует миграции.

Перед запросом редактору записывается уникальный Audit claim PostgreSQL;
перезапуск и потеря ledger не разрешают повтор. Полный вход, raw редактора,
полный вычисленный diff и доказательства каждой новой проверки хранятся в ignored data.
Перед и после проверки сверяются источник, политика, промпты, прежний trace,
кандидат, адресат, пауза и leases. Незавершённая коррекция не получает policy
approval, даже если падение произошло после создания известного DRAFT.
Дедупликация, исходный час, ограничение 3600 секунд и обработчик отправки прежние.

Таблица `editorial_control` содержит общую паузу, настройки и рабочий статус.
Revision меняется при управлении и настройке, но не от heartbeat. Настройки
изменяются на паузе. Новая политика не переодобряет старые human-черновики.

`editorial_article_ledger` хранит полный прежний журнал с сохранёнными ID,
отказами, часами, hashes и отменёнными источниками. Импорт идемпотентен, запись
защищена CAS. Старый JSON сохраняется как резервная копия; marker запрещает
возврат к нему при потере записи PostgreSQL. Остальные таблицы `hub_*` сохраняют
историю и связи. Историческое имя таблицы не означает работающую панель Hub.

Postiz BFF проверяет штатную cookie-сессию, активного SUPERADMIN, закреплённые
ID пользователя и организации, Origin/Referer. Внутренний API принимает отдельный
машинный ключ и эти ID. Browser не получает ключ. Отдельных human approval
endpoints в новом API нет. `/owner-browser/` использует ту же сессию Postiz для
восстановления входа в MAX; закрытые браузерные порты не становятся публичными.

## Источники

Режим Postiz «Открытая наука» объединяет NASA SVS, NOIRLab Image of the Week
и ESA/Hubble Picture of the Week. Приоритет вращается по общему календарному
часу; из всех кандидатов подготавливается одна новая статья. Известный отказ
GET не вызывает повтор этого запроса и позволяет проверить следующий источник.
Повреждённые журнал, checkpoint или корпус дедупликации останавливают весь цикл.
Фильтры авторов/организаций, ключевых слов и предела длины общие. Для совместимости
они хранятся в прежнем блоке настроек `nasa`; новая панель сохраняет все его поля.
Рейтинг у этих источников отсутствует и остаётся равным нулю.

С 27 октября 2026 рабочий предел полного исходника — 350 английских слов.
Прежний начальный предел 180 оставлял резерв без кандидатов: read-only проверка
неиспользованных корректных подписей дала 305–404 слова. Более длинная статья
пропускается при отборе без обрезания содержания. Русский пост по-прежнему
ограничен 3500 символами, все проверки качества, прав и дедупликации сохраняются.
Предел меняется штатной настройкой `nasa.max_words` только на общей паузе.

NOIRLab и ESA/Hubble: разрешены только полные научные текстовые подписи из
указанных разделов; научные статьи, музыка, логотипы и медиа не включаются.
Официальные условия [NOIRLab](https://noirlab.edu/public/copyright/) и
[ESA/Hubble](https://esahubble.org/copyright/) выпускают эти тексты по CC BY 4.0,
которая разрешает переводы и распространение адаптированного материала.
В каждом посте обязательны название организации, исходный URL, ссылка на
лицензию и пометка машинного перевода и редактирования. Этот footer включён
в согласованный snapshot, но отделён от научного текста при проверке чисел.
Изменённый footer, неподтверждённые числа самого перевода и прочие quality gates
продолжают блокировать отправку.

Перед переводом сохраняются исходные HTML каталога, страницы, условий, credits,
все literal href и hashes. Проверяется полный нормализованный текст условий,
а не только ссылка на CC в навигации. Его изменение требует новой проверки
прав; стороннее copyright-исключение блокирует статью. У новых источников
отдельные PG cursors, а URL, исходники и пятисловные повторы сверяются с общей
историей, включая отмены и прежние исключения NASA. Нет восстановления старых
записей или сокращения оригинала до установленного числа слов.
GET используют отдельные соединения: на рабочей VM повторное использование
соединения зависало после успешного каталога. Чтение ограничено 60 секундами,
подключение — 10; сетевой отказ не вызывает повтора того же запроса. HTTP
401/403/429 и challenge блокируют источник с сохранением checkpoint.

Пример двух отключённых источников — `config/science_sources.example.json`.
Профиль `server_science` обозначает встроенный строгий сборщик; общий HTML-парсер
отклоняет его до сетевого запроса. Файл CSS-селекторов для него не используется.
На рабочей VM они включаются отдельно после проверки прав и доступа; старый
NASA policy-файл не переписывается. Старые human DRAFT после изменения реестра
могут требовать новой проверки конфигурации: их historical hashes не освежаются.

NASA: полный narrative из официального API, все HTML-ссылки, credits/права,
давность, авторы, ключевые слова, дедуп по истории, hash и пятисловным цепочкам.
Материал не обрезается. Архивные материалы сохраняют дату и не называются
свежими новостями. NASA не предоставляет проверенный рейтинг: ненулевой
`min_rating` блокирует подбор вместо выдуманного значения.
Начальный предел 300 английских слов снижает риск превышения лимита MAX после
перевода; окончательный лимит проверяется по русскому тексту. Пагинация ограничена
по запросам, а отдельный PostgreSQL cursor продолжает подбор после перезапуска,
сначала проверяя новые материалы в начале каталога.

Reddit: подготовлен OAuth-сборщик с subreddit/author scope, ключевыми словами,
минимумом score/comments, давностью, сортировкой и ограниченной пагинацией.
Crosspost проверяется по оригиналу, права привязаны к конкретному посту/автору
и исходному hash. API-доступ и разрешение на внешние переводы не выдаются через
обычную форму настроек. Неодобренный Reddit остаётся выключенным. Штатный
публикующий режим включает только указанные научные источники; допуск Reddit к публикации требует
отдельной доверенной source policy с сохранением per-post прав и обработки
удалений. Локальные фикстуры не подтверждают живой доступ Reddit.

## Историческая процедура переключения на 0.7.0

1. Сверить sending/unknown/leases, Postiz и фактический MAX; сохранить закрытую
   копию обеих БД, ledger/traces, настроек и units. Остановить desktop heartbeat.
2. Проверить исходники/тесты, собрать закреплённый образ
   `max-postiz-linux:0.7.0-editorial`, сохранить старый образ для отката.
3. Установить Python source/import/distribution 0.7.0 и миграцию 0007.
   `editorial-agent migrate` переносит журнал, оставляя общую паузу.
4. Проверить новый внутренний API без второго обработчика. Переключить bridge
   Postiz, штатную аутентификацию и reverse proxy. После проверки отключить
   старый `max-postiz-hub.service` и внешний 8090; состояние не удалять.
5. Запустить один новый systemd-сервис. Из Postiz проверить настройки,
   pause/start, враждебный Origin и недоступность чужого пользователя.
6. Подтвердить один полный цикл: source → Hy → Ministral → LT → тот же Postiz
   DRAFT/QUEUE → policy approval → verified dispatch → PUBLISHED → exact MAX.
   Между доставками max_test paused, остальные адресаты постоянно paused.
7. Перезапустить сервис и проверить неизменность истории, сохранение паузы и
   отсутствие повторного dispatch. Живые результаты фиксируются отдельно.

При откате сначала остановить новый обработчик и сверить все внешние исходы.
Не возвращать старый JSON как авторитетный журнал после PostgreSQL migration.
Старые приложения допускается запускать только с совместимой БД и общей паузой;
восстановление резервной копии выполняется в отдельную пустую установку.
