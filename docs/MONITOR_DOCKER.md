# Служебный монитор MAX в Docker

Контейнер содержит служебный отправщик, Linux Chromium и наблюдатель редакционной VM.
Он читает тот же формат служебной SQLite, что и Windows-сборщик. Рабочий цикл статей остаётся на редакционной VM.
Отдельный контейнер сборщика берёт статус по SSH с проверкой host key,
PID/startticks, ревизии, manifest и хешей установленных runtime-файлов.
Скрипт выполняется от `editorial` и запрашивает GET `/health`,
`/internal/editorial/state` и `/internal/editorial/routes` с проверкой владельца.
Отправщик с Chromium получает только очищенный снимок, доступный для чтения.
Обычный ключ `editorial` позволяет выполнить произвольную команду от имени
рабочего пользователя VM. Перед продакшном нужен отдельный ключ, который сама
VM ограничивает одной проверенной командой чтения. Разделение контейнеров
изолирует ключ от Chromium на хосте сборщика.
Внешний watchdog всей домашней сети требует отдельного хоста.

## Сборка и тома

Используйте отдельные каталоги на смонтированном массиве и UID/GID 10460. Убедитесь,
что Docker и containerd запускаются после монтирования массива. Для существующего
Docker перенос его данных требует отдельной процедуры. У пустой установки настройте
`data-root` Docker и `root` containerd, сохранив исходные конфиги.

Создайте каталоги `state`, `chromium`, `private`, `source-ssh` и `snapshot`.
До запуска Compose создайте также `state/config`, `state/data`,
`state/data/monitor` и `state/data/monitor/browser-runtime` с владельцем 10460:10460.
Точки монтирования заданы явными путями. Профиль Chromium, блокировка профиля
и его квитанции живут вместе в `chromium`.
Служебный SQLite хранится отдельно в `state/data/monitor/monitor.sqlite`.
Права на каталоги и локальные SSH-файлы ограничьте владельцем процесса.
Скопируйте действующую служебную конфигурацию в `state/config/monitor.json`,
установите `channel=chromium` и `headless=true`. Используйте один проверенный
закрытый канал и выключите команды и ответы в управляющий чат.

В `source-ssh` положите `known_hosts` с проверенным ключом VM и `id_ed25519`
для SSH-доступа. В `private/source.local.json` запишите объект
`host`, `known_hosts_sha256` и `source`. В `source` укажите
`binding=pinned-editorial-monitor-v1`, `minimum_revision`, один объект в `profiles`
с `version`, `source_commit`, `pid`, `start_ticks`, `runtime_count`,
`manifest_path`, `manifest_sha256`. Поле `database` содержит только ожидаемые
`host`, `port`, `database` и `user`. Пароли БД остаются на VM.
После смены PID или версии остановите отправщик, обновите pins и пересоздайте
сборщик. Сверьте новый снимок. Прежний binding — поле JSON `binding` записи
`container_report_sender_v1` таблицы `monitor_meta` в SQLite.
Команда `… run --rm --no-deps monitor rebind --expected-binding <old-binding>` сохраняет прежнее
доказательство и применяет новую привязку только при закрытой очереди,
штатном состоянии отправителя и сохранении доступа к тому же каналу.

Установите `MONITOR_STATE`, `MONITOR_PROFILE`, `MONITOR_PRIVATE`,
`MONITOR_SOURCE_SSH` и `MONITOR_SNAPSHOT`.
Укажите `MONITOR_PYTHON_BASE` с digest базового образа. Из корня checkout выполните:

```sh
docker compose -f deployment/monitor/compose.yaml config --quiet
docker compose -f deployment/monitor/compose.yaml build monitor
```

Chromium работает с sandbox от непривилегированного пользователя. Применяется
профиль seccomp на основе [Playwright 1.63.0](https://github.com/microsoft/playwright/blob/v1.63.0/utils/docker/seccomp_profile.json).
Профиль изменён для `chroot` во вложенном пространстве имён Chromium.
Лицензия исходного профиля находится в `deployment/monitor/LICENSE.playwright`.
Образ устанавливает Playwright из `requirements-browser.lock` и его Chromium.
Рабочий контейнер не публикует порты и запускается после перезагрузки через
политику Docker `unless-stopped`. Инструменты noVNC и Xvfb входят в отдельный образ. Для входа владельца профиль
Compose `login` публикует noVNC только на loopback. Создайте файл `private/vnc-password` через
`x11vnc -storepasswd`, соберите `docker compose … --profile login build login`, затем запустите профиль
и откройте страницу через SSH-туннель.
Остановите контейнер входа перед проверкой прав и отправкой.

Для переноса проверенной сборки 0.14.6 на другой Linux amd64 используйте
оба архива выпуска. Проверьте их по `SHA256SUMS`, распакуйте исходный архив
и загрузите готовые образы через `docker load -i max-postiz-monitor-0.14.6-linux-amd64-images.tar.gz`.
Задайте пути к своим каталогам и запускайте Compose с `--no-build`.
Архив образов позволяет повторить установку без доступа к репозиториям
системных пакетов. При сборке заново системные пакеты берутся из доступных
репозиториев Debian.

## Перенос с Windows

1. Проверьте Chromium и сборщик на отдельной копии. Для подготовки Linux-профиля
   используйте отдельное тестовое состояние. Скопируйте историю Windows после
   кооперативной остановки прежнего процесса, сверки отсутствия `pending`,
   `sending` и `unknown` и проверки резервной копии SQLite. Сохраните исходную
   папку журнала браузера как архив. Вход в MAX выполните в Linux-профиле.
2. Положите проверенный отдельный SQLite backup без файлов WAL, SHM и journal
   в закрытый каталог `private`,
   выполните `docker compose … run --rm --no-deps monitor init --seed /run/monitor/seed.sqlite
   --seed-sha256 <sha>`. Сверьте историю и удалите временный файл переноса
   из каталога секретов после сохранения отдельной резервной копии.
3. После отдельной проверки SSH запустите `docker compose … up -d --no-build collector`.
   Выполните `… run --rm --no-deps monitor preview` и `… run --rm --no-deps monitor inspect`.
   Подтвердите точный источник и доступ к заданному каналу.
4. Когда право отправки передано новому контейнеру и прежний отправщик остановлен,
   выполните `… monitor arm`, затем один раз `… monitor trial`. Команда фиксирует
   попытку до отправки и читает точный отчёт в новом браузерном сеансе. При
   неизвестном исходе сохраните outbox и браузерную квитанцию для сверки.
5. После `verified` запустите `docker compose … up -d monitor`. При отсутствии
   подтверждённого права контейнер собирает состояние. После сбоя отправителя
   сбор продолжится с сохранением блокировки и журнала. Состояние SQLite и
   профиль сохраняются при пересоздании. Кооперативная остановка даёт браузеру
   завершить начатую операцию. Для возврата сначала остановите контейнер,
   сверяйте неизвестные исходы и перенесите обновлённую историю.

Файлы конфигурации площадки, профиль, SSH-ключи и рабочие отчёты хранятся
за пределами исходного архива.
